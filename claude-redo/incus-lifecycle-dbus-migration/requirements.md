# Requirements: incus-lifecycle-dbus-migration

## Purpose

Every Incus container's start/stop lifecycle is currently driven by raw `incus`
CLI calls (`incus start`, `incus stop`, `incus list -f csv`) inside host runit
`run`/`finish`/`check` scripts. This violates the repo's core invariant
("D-Bus is the only control plane... no `Command::new(...)` subprocesses...
for live state") even though a fully-formed `incus` D-Bus plugin already
exists and exposes real lifecycle mutations. This spec closes the gap so
container start/stop goes through `org.opdbus.v1.plugins.incus`, with an
audited, blockchain-backed mutation trail, instead of bypassing the control
plane.

Scope is the six container lifecycle runit services
(`incus-ct-{xray,netmaker,cozo,qdrant,mail-3tched,assistant}`) and the
`incus` plugin's D-Bus surface. Container-internal supervision (systemd
inside each container) is explicitly out of scope — see Non-Goals.

## Context and Verified Baseline

### Live host state (post-outage recheck, 2026-08-03)

- Six runit definitions exist at `/etc/runit/sv/incus-ct-<name>/` (one per
  container), each with `run`, `finish`, `check`, and `log/run`, generated by
  `/usr/local/bin/3tched-incus-svcgen` (source: `deploy/runit/3tched-incus-svcgen`).
  The `incus-ct-xray` and `incus-ct-netmaker` services currently report
  `down`, even though both containers are `RUNNING`; the lifecycle definitions
  are not presently the authority for those running instances.
- `incus list` currently reports `xray`, `NetMaker`, `cozo`, `qdrant`, and
  `mail-3tched` running, while `assistant` is stopped. The earlier claim that
  all six production containers were running is stale.
- To regain connectivity after the network outage, the operator deliberately
  deleted the OVS bridge and restored direct `eth0` as the emergency fallback;
  xray and NetMaker consequently have only loopback in their network
  namespaces. No lifecycle rollout, production-container
  restart, or `op-grpc-bridge` restart is permitted from this spec until the
  separate network recovery gate in `netclient-container-netns` is satisfied.
- `run` shells directly to `incus start "$NAME"` and polls
  `incus list -f csv -c ns | grep RUNNING` in a `while` loop; `finish` calls
  `incus stop "$NAME"`; `check` runs `incus list -f csv -c ns | grep RUNNING`.
  None of these three scripts touch D-Bus at all today.
- Only `deploy/runit/incus-ct-netmaker/run` and (as of this session)
  `deploy/runit/incus-ct-xray/{run,finish,check,log/run}` are checked into the
  repo; the other four containers' service definitions exist only live on the
  host, untracked.
- The checked-in `incus-ct-netmaker/run` is a **different, older generation**
  of the script that *does* call `busctl` against
  `org.opdbus.v1.plugins`/`/org/opdbus/v1/plugins/incus`
  (`org.opdbus.v1.PluginV1.Call` with `start_instance`/`stop_instance`
  payloads) — proving a D-Bus-driven version of this script existed before
  and was later replaced by the raw-CLI generator output, not the other way
  around.

### The `incus` plugin already implements real lifecycle mutations

`crates/op-plugins/src/state_plugins/incus.rs` registers on
`/org/opdbus/v1/plugins/incus` via `org.opdbus.v1.PluginV1` (`Call`, method
signature `ss` → `s`, JSON tool-name + JSON args in, JSON string out).
`incus_schema()` (line ~1617) declares these methods, **all** tagged
`op_state_store::SideEffect::Mutation`: `create_instance`, `modify_instance`,
`delete_instance`, `start_instance`, `stop_instance`, `restart_instance`,
`freeze_instance`, `unfreeze_instance`, `snapshot_instance`,
`restore_snapshot`, `rename_instance`, `set_instance_config`, `exec_instance`,
plus device methods (`add_device`/`remove_device`/`update_device`). Each
carries a `cap.service.incus.instance.*@v1` capability id and a
`mut.service.incus.instance.*@v1` subid.

`start_instance`/`stop_instance`/`restart_instance` (`StartInstanceInput`
`{name}`, `StopInstanceInput` `{name, force}`) resolve the given name against
a **live** `GET /1.0/instances?recursion=1` call (`Self::resolve`, line ~333)
and then issue a real `PUT /1.0/instances/{name}/state` with
`{"action":"start"|"stop"}` (`set_instance_running`, line ~397, via
`incus_api_call`, line ~264) — this is a genuine live Incus API call, not a
toggle on cached plugin state.

**No read-only method exists.** Every method in `incus_schema()` is
`SideEffect::Mutation`; there is no `list_instances`/`get_instance_state`
tool. Confirmed live: `busctl ... Call ss list_instances '{}'` →
`Call failed: list_instances`; same for `get_schema`. `GetAllProperties`
returns `schema.example` (line ~1626) — a **hardcoded documentation sample**
(`privacy-user-123`, `netmaker` lowercase) — not live state; it does not
include `xray`, `cozo`, `qdrant`, `mail-3tched`, `assistant`, or the real
`NetMaker` (capitalized) container at all. Any status check must go through
one of the mutation methods' resolve step or fall back to `incus list`
directly; there is nothing safe to poll today.

### Mutation calls are rejected for a plain caller — the real blocker

Live tests against the real running `cozo` container (idempotent: calling
`start_instance` on an already-`Running` instance is a no-op from Incus's
perspective):

```
$ busctl --address="unix:path=/run/opdbus/session-bus.sock" call \
    org.opdbus.v1.plugins /org/opdbus/v1/plugins/incus \
    org.opdbus.v1.PluginV1 Call ss start_instance '{"name":"cozo"}'
Call failed: Access denied              # as regular user (jeremy)

$ sudo busctl ... (same call)
(exit 1, no stderr at all)              # as root
```

Per CLAUDE.md's zero-trust model, `mut.*` methods require an `actor_id` +
`capability_id` derived from the WireGuard-identity session flow. A bare
shell `busctl`/`zbusctl` call — from an interactive user *or* from a
boot-time root process with no WireGuard session — carries neither, so the
capability check correctly rejects it. This is the actual reason the runit
scripts use raw `incus` CLI today: not an oversight, but a real
unsolved-until-now auth gap for local, non-WG-identified, boot-time callers.

### A system-bus transport precedent exists, but it is not an auth bypass

`/run/dbus/system_bus_socket` (the real, standard system bus — distinct from
the custom `/run/opdbus/session-bus.sock`) carries
`org.opdbus.v1.plugins.openflow`, owned by `op-of-controller` (confirmed via
`busctl --system list`). The actual server registration is in
`crates/op-network/src/bin/op-of-controller.rs`; the similarly named code in
`state_plugins/openflow.rs` is its client proxy.

Phase 0 located the generic gate in
`crates/op-grpc-bridge/src/schema_router.rs`. It is bus-agnostic and checks the
process-global identity sled footprint, not the D-Bus sender UID. Registering
the same generic Incus object on the system bus therefore does not solve the
problem. The selected design is a filtered system-bus adapter that exposes
only lifecycle/status methods, resolves the D-Bus sender UID, requires UID 0,
and reuses the audited native dispatcher. The session-bus gate remains
unchanged.

## Functional Requirements

### FR-1: Root/boot-time callers can invoke incus lifecycle mutations

A caller with no WireGuard session — specifically, a root-owned process on the
real system bus connecting the way a runit `run`/`finish` script would at boot — can
successfully call `start_instance`, `stop_instance`, and `restart_instance`
against the real, running `incus` plugin and have it take effect against the
live Incus API.

**Acceptance criteria**: from a root shell with no WG/session-bus identity
established, calling `stop_instance`/`start_instance` on a disposable test
container (not one of the six production containers) via `busctl`/`zbusctl`
returns success (not "Access denied", not a silent failure), and
`incus list` reflects the resulting state change.

### FR-2: A read-only instance-status method exists

`incus_schema()` gains a `SideEffect::Read` method — e.g.
`get_instance_state` (`{name}` → `{name, status, running}`) — backed by the
same live `GET /1.0/instances/{name}/state` call `Self::resolve`/
`set_instance_running` already use for resolution, so runit's polling loop
and `check` script have a real D-Bus-native status source instead of no
option at all.

**Acceptance criteria**: `busctl --system ... Call ss get_instance_state
'{"name":"xray"}'` returns live status for a real container to UID 0 without
requiring a WireGuard identity. The session-bus route still requires
`cap.service.incus.instance.read@v1`. Schema tests cover the method,
`SideEffect::Read`, typed output, and the native dispatcher.

### FR-3: All six container runit services are D-Bus-driven

`/etc/runit/sv/incus-ct-<name>/{run,finish,check}` for
`xray, netmaker, cozo, qdrant, mail-3tched, assistant` call `busctl`/`zbusctl`
against the `incus` plugin (`start_instance`/`stop_instance`/
`get_instance_state`) instead of raw `incus start`/`incus stop`/`incus list`.
`log/run` is unaffected (it never touched `incus` directly).

**Acceptance criteria**: `grep -rn 'incus start\|incus stop\|incus list' /etc/runit/sv/incus-ct-*/{run,finish,check}`
returns no matches after the change; each of the six services restarts
cleanly under `sudo sv restart incus-ct-<name>` one at a time, verified against
live host state before/after (not assumed).

### FR-4: Repo parity for all six services

`deploy/runit/incus-ct-<name>/{run,finish,check,log/run}` is checked in and
reviewed for all six containers (currently only `xray` and a stale `netmaker`
exist) before publication. The normal golden/live btrfs publisher installs
them; no hand-copy deployment is allowed. Each repository file is
byte-identical to its corresponding live `/etc/runit/sv/incus-ct-<name>/`
file after FR-3 lands.

**Acceptance criteria**: `diff` between each repo file and its live
counterpart is empty for all six containers, all four file types.

### FR-5: Generator template updated

`deploy/runit/3tched-incus-svcgen` — the actual generator that produced the
raw-CLI scripts live — is updated to emit the D-Bus-driven `run`/`finish`/
`check` content, so re-running it (e.g. `3tched-incus-svcgen --all-named`)
does not regress FR-3 back to raw CLI calls.

**Acceptance criteria**: running `3tched-incus-svcgen <name> --no-enable` on
a scratch name produces a `run` script containing `busctl`/`zbusctl` calls,
not `incus start`/`incus stop`.

## Non-Functional Requirements

- **NFR-1: No live restarts of production containers during design/discovery.**
  FR-1's acceptance test uses a disposable test container, never `xray`,
  `netmaker`, `mail-3tched`, `qdrant`, `cozo`, or `assistant`.
- **NFR-2: One container restarted at a time, verified, before the next.**
  When FR-3 lands for real, each `incus-ct-<name>` is restarted individually
  with live verification (`sudo sv status`, `incus list`, and — for `xray`
  specifically — a real TLS/SNI request through it) before moving to the
  next; a mid-sequence failure must not be compounded by touching more
  services.
- **NFR-3: No weakening of the session-bus identity gate.** Whatever
  mechanism grants root/boot-time callers access (system-bus registration,
  a scoped local-root capability, or otherwise) must not make
  `mut.service.incus.instance.*` callable by an arbitrary WG-identified
  session that previously lacked the capability — the fix is additive for a
  new caller class, not a relaxation of the existing one.
- **NFR-4: Behaviour-preserving.** Container start/stop/restart/health-check
  semantics stay equivalent to today's raw-CLI scripts; only the mechanism
  changes.
- **NFR-5: OSCAL subids** for new surfaces:
  - `get_instance_state` query method — `obs.service.incus.instance.state@v1`
  - system-bus (or equivalent) registration for `incus` — `src.service.incus.system-bus@v1`
- **NFR-6: Post-outage rollout gate.** Code, unit tests, and isolated-bus tests
  may proceed, but no production container, OVS/uplink service, or
  `op-grpc-bridge` service may be restarted until the network recovery spec
  has restored and re-verified the base topology. `op-grpc-bridge` currently
  binds `10.200.0.2`, which is absent in fallback state.

## Non-Goals

- **Container-internal process supervision.** `xray`/`netmaker`/others run
  systemd inside the container to supervise their own workload process
  (confirmed intentional — prevents races between runit's container-lifecycle
  loop and in-container process supervision). Not touched by this spec.
- **The `netmaker` D-Bus adapter plugin(s)** (`op-grpc-adapters/src/adapters/netmaker.rs`,
  `op-plugins/.../netmaker.rs`) and any non-lifecycle Incus device management
  (proxy devices, snapshots, device add/remove) beyond what FR-1/FR-2 need to
  verify the auth fix.
- **`op-ovsbr0-setup`/OVS bridge topology** — unrelated to container
  start/stop; already covered by the CLAUDE.md doc fix landed earlier this
  session.
- **Rewriting `incus.rs`'s declarative "instances" example/config data** —
  the stale `schema.example` (`privacy-user-123`, lowercase `netmaker`) is
  documentation-only and unrelated to how `start_instance`/`stop_instance`
  actually resolve names; not touched.
