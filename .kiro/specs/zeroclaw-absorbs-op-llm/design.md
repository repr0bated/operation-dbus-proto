# Design — zeroclaw-absorbs-op-llm

---

## 1. Ownership Boundary

### Zeroclaw plugin — sole authority

```
crates/op-plugins/src/state_plugins/zeroclaw.rs          ← ZeroclawPlugin, ZeroclawState
crates/op-plugins/src/state_plugins/common/llm_projection.rs  ← shared schema types
crates/op-plugins/src/state_plugins/plugin_schema_defs.rs     ← schema aggregator/re-export
```

Zeroclaw owns every runtime LLM concern:

| Concern | Owner |
|---|---|
| Provider catalog | `ZeroclawState::projection.providers[]` |
| Model route table | `ZeroclawState::projection.model_routes[]` |
| Selected provider | `ZeroclawState::selected_provider` |
| Selected model | `ZeroclawState::selected_model` |
| Automatic selector policy | `ZeroclawState::selector_policy` (new) |
| Router / classifier config | `ZeroclawState::projection.router` |
| Tool declarations | `ZeroclawState::projection.tools[]` |
| Structured output policy | `ZeroclawState::projection.structured_output` |
| Transport metadata | `ZeroclawState::transport` |
| Availability / health | per-`ModelRoute.available` + new `health_status` field |
| Cost metadata | new `ModelRoute.cost_profile` field (budget-class string, unit-neutral) + request-side `SelectionInput.cost_policy` |
| Effort metadata | new `ModelRoute.effort_level` |
| Privacy / compliance tier | new `ModelRoute.privacy_tier` |
| Fallback chain | new `ModelRoute.fallback_routes[]` |
| Execution authorization | Zeroclaw D-Bus method `AuthorizeExecution` |

### What is NOT owned by Zeroclaw

- Message persistence and session history — `op-chat` / `op-cozo-store`
- Semantic memory — `op-cognitive-mcp`
- gRPC bridge topology — `op-grpc-bridge`
- Web surface — `op-web`
- Identity — `op-identity`

## 2. The Schema = The Plugin = The Contract

The Zeroclaw plugin IS its `PluginSchema`. The schema is the single source of
truth for D-Bus method generation, MCP tool declarations, gRPC shape
derivation, and UI field rendering. `SchemaEngine` (in `op-projection`) owns
schema registration and the **one** projection; `MutationEngine` owns validated
state mutations against `PluginSchema`. D-Bus objects are generated from
`PluginSchema` by the gRPC bridge — per-plugin hand-written D-Bus plumbing is
not required.

The `PluginSchema` field set is generated **entirely** from `schemars` via the
`plugin_schema_from_schemars::<ZeroclawState>()` converter (spec §8), which
replaces the legacy `schema_from_state()` introspection for Zeroclaw. Only the
method/signal/guarantee declarations and the `subids` map are supplied
explicitly (via PR #14's `with_caps`); every field comes from
`schemars::schema_for!(ZeroclawState)`.

```
PluginSchema (in plugin_schema_defs.rs)
    └─ ZeroclawState (serde + schemars)
          ├─ LlmProjection (flattened)
          │     ├─ providers: Vec<Provider>
          │     ├─ model_routes: Vec<ModelRoute>    ← extended with cost/effort/privacy fields
          │     ├─ router: Router
          │     ├─ tools: Vec<LlmTool>
          │     ├─ structured_output: StructuredOutput
          │     ├─ config_schema: ConfigSchema
          │     └─ ui_surface: UiSurface
          ├─ selected_provider: String
          ├─ selected_model: String
          ├─ transport: LlmTransport
          └─ selector_policy: SelectorPolicy  ← new
```

The schema is generated by `schemars` from these types. It is re-exported
through `plugin_schema_defs.rs`. If a provider/model/tool/route is not in this
schema projection, it does not exist and cannot execute.

## 4. Automatic Model Selection Algorithm

Input (`SelectionInput`):

```
task_class:          String         // "code", "chat", "reasoning", "vision", ...
requested_effort:    String         // "low", "medium", "high", "max"
cost_policy:         Option<String> // budget-class / cost-ceiling policy (unit-neutral); None = no limit
latency_target:      Option<String> // "interactive", "batch", None
context_tokens:      u32            // estimated token count
privacy_tier:        String         // "public", "internal", "confidential"
tool_needs:          Vec<String>    // tool names required
explicit_provider:   Option<String> // authorized override
explicit_model:      Option<String> // authorized override
```

Phase 1 — Hard Filters (applied in order, all must pass):

1. Route declared in `model_routes[]` — else reject.
2. `available == true` — else skip.
3. `privacy_tier` ≤ request tier — else skip.
4. Tool needs satisfied (`tools[]` declared) — else skip.
5. `context_window ≥ context_tokens` — else skip.
6. Route's `cost_profile` (budget class) satisfies `cost_policy` when set —
   string/budget-class comparison only. **No `cost_per_token` or unit math.**

Phase 2 — Scoring (higher = better, all values from schema state):

```
score = capability_match_bonus
      + effort_quality_score(route.effort_level, requested_effort)
      - cost_weight * cost_rank(route.cost_profile)   // budget-class rank, unit-neutral
      - latency_penalty(route.latency_class, latency_target)
      + route_health_bonus(route.available, route.health_score)
```

`cost_profile` is the confirmed Zeroclaw-native cost field — a budget-class
string (spec §2a). `cost_rank(...)` maps the budget class to an ordinal; there
is no per-token or currency math anywhere in the selection path.

Phase 3 — Output (`SelectionOutput`):

```
selected_provider:  String
selected_model:     String
reason:             String
estimated_cost:     Option<String>  // Zeroclaw-native units (unit-neutral string)
effort_level:       String
confidence:         f64        // 0.0–1.0
fallback_routes:    Vec<String>  // ordered hints of next-best routes
event_metadata:     { trace_id, timestamp, selector_version }
```

The algorithm reads exclusively from `ZeroclawState` fields projected via
D-Bus. No `match` arm on `ProviderType` enum in the selection path.

## 5. Provider Adapter Absorption

The six adapters in `op-llm` (Anthropic, Gemini, GeminiCli, Factory,
OpenClaw, GCloudADC) plus `AssistantProvider` are moved into the module
owned by the architecture boundary that holds Zeroclaw execution logic.
They become private implementation details behind the Zeroclaw D-Bus surface.
Factory is treated as a provider category in Zeroclaw's provider catalog —
one among many (OpenRouter, Kilocode, Opencode, etc.) — not a separate D-Bus
control object or BYOM control plane.

The exact target module is confirmed by the Schema Agent and D-Bus Agent
handoffs after inspecting the SchemaEngine/MutationEngine/gRPC-bridge dispatch
boundary. The Provider Absorption Agent MUST NOT create a new crate and MUST
NOT place adapter implementation inside `op-plugins` in a way that makes the
schema crate own runtime HTTP/adapter behavior; the execution host module is
separate from `PluginSchema` authority.

Absorption steps:
1. Identify target module via Schema Agent handoff (pre-implementation spike).
2. Move adapter source files; update `mod` declarations; fix imports.
3. Remove `op-llm` from workspace `Cargo.toml` after all callers are migrated.
4. No behavior changes to adapters during absorption — behavioral parity is
   validated by existing adapter tests, now run from the new location.

A compatibility re-export shim (`pub use`) inside `op-llm` MAY exist
temporarily to avoid breaking callers mid-migration. The shim is removed
in the final Caller Migration phase.

## 6. Single Projection + gRPC-Bridge D-Bus View

There is **exactly one** projection of Zeroclaw, owned by
`op-projection::SchemaEngine` (the `ShmWriter` introduced in PR #14). The D-Bus
object tree, the `/dev/shm` files, and the gRPC stream are all **views** of that
one in-memory `PluginSchema` — never a second computation or a second writer.
Full normative detail is in **spec §1.1, §7, §9, §10**; this section is the
design summary.

```
op-projection::SchemaEngine  (sole owner of the in-memory PluginSchema)
   │
   ├─(view A) GrpcBridgeProjectionHook → D-Bus object tree  ← PRIMARY call surface
   │            /org/opdbus/v1/plugins/zeroclaw[/routes/<hint>|/providers/<id>]
   ├─(view B) ShmWriter → /dev/shm/opdbus/schemas/zeroclaw.json   ← discovery snapshot only
   │            + /dev/shm/live-schema.json (aggregate)            ← never read back on any path
   └─(view C) SchemaPassthroughService → gRPC ZeroclawProjection   ← remote subscribers
```

### Observer wiring (no crate cycle)
`SchemaEngine` lives in `op-projection`; the bridge hook lives in
`op-grpc-bridge`. To keep the dependency edge one-directional
(`op-grpc-bridge → op-projection`):

- `op-projection` defines `trait SchemaProjectionObserver { fn
  on_zeroclaw_projection(&self, schema: &PluginSchema, state: &ZeroclawState); }`
  and `SchemaEngine` invokes registered observers after each projection cycle,
  passing the **in-memory** schema/state.
- `op-grpc-bridge`'s `GrpcBridgeProjectionHook` implements the trait and is
  registered at startup. `op-projection` has **no** dependency on
  `op-grpc-bridge`.

### `/dev/shm` is a snapshot, not an authority
- **`SchemaEngine`/`ShmWriter` is the sole writer**; writes are atomic
  (`.tmp` + `rename`). Individual plugins NEVER write any `/dev/shm` file.
- The D-Bus tree is built from the in-memory `PluginSchema` handed to the
  observer — **never** by reading `zeroclaw.json` back.
- `op-chat`, MCP, and Refactro use D-Bus (or the gRPC stream) for execution-path
  decisions. The `/dev/shm` file is discovery/inspection only.

**Invariants:**
- Snapshot absent → SchemaEngine hasn't registered Zeroclaw; the D-Bus tree is
  likewise absent; callers wait.
- Snapshot stale (mtime > 30 s) → log warning; it is non-authoritative anyway.

## 8. Layer Boundaries

Two bad outcomes this architecture explicitly prevents:
1. `op-llm` survives as a hidden authority under a new name.
2. `op-plugins` becomes a runtime blob mixing provider HTTP clients with schema authority.

### Layer 1 — Zeroclaw Contract Layer

**Location:** `crates/op-plugins/src/state_plugins/` (zeroclaw.rs, plugin_schema_defs.rs, common/llm_projection.rs)

**Owns:**
- `PluginSchema` definition for Zeroclaw
- `ZeroclawState` and all nested schema types
- Route declarations, provider catalog declarations, selector policy schema
- OSCAL subid annotations
- Generated D-Bus surface (properties, methods, signals derived from PluginSchema)
- `/dev/shm/opdbus/schemas/zeroclaw.json` projection spec (written by SchemaEngine, not by plugin code)

**The Zeroclaw plugin IS its PluginSchema. The schema IS the plugin. PluginSchema is the single source of truth for all calls.**

**Must NOT contain:** provider HTTP client implementations, network adapter code, wire-format parsing, streaming logic, or auth header construction.

### Layer 2 — Zeroclaw Orchestration Layer

**Location:** Module hosting Zeroclaw execution logic (confirmed by Provider Absorption Agent spike), e.g. `common/selector.rs` and D-Bus method handlers in `zeroclaw.rs`.

**Owns:**
- Dynamic model selection (`select_model` pure function)
- Effort/cost scoring, route resolution
- Execution authorization (`AuthorizeExecution`)
- Fallback planning
- `MutationEngine` integration for validated state mutations
- Trace/event emission (`evt.*` signals)
- Handoff to provider adapters (passes an execution plan, not a raw request)

**Reads effective contract/state only through SchemaEngine / MutationEngine / D-Bus generated from PluginSchema. Does NOT implement provider wire formats directly.**

### Layer 3 — Provider Adapter Layer

**Location:** Execution host module identified by the Provider Absorption Agent spike (NOT inside `op-plugins` schema authority if that would mix runtime I/O with PluginSchema ownership).

**Owns:**
- OpenAI / Anthropic / Gemini / OpenClaw / Factory / Kilocode / Opencode / OpenRouter / GCloudADC wire formats
- Request/response conversion and streaming parsing
- Auth header construction and network calls

**Hard constraints:**
- Cannot select models, mutate routes, read live state, bypass D-Bus, or execute undeclared schema routes.
- Takes only a schema-authorized execution plan from the Orchestration Layer.
- Must not call back into route selection, selector policy, or MutationEngine.
- Must not read `/dev/shm` paths or query D-Bus for live state decisions.
- Provider adapters are replaceable implementation details under Zeroclaw authority.

### Dependency Direction

```
Contract Layer (PluginSchema, ZeroclawState, schema types)
       ↓ defines schema and generated D-Bus surface
Orchestration Layer (select_model, AuthorizeExecution, MutationEngine integration)
       ↓ consumes contract/state; produces execution plan
Provider Adapter Layer (HTTP clients, wire formats, streaming)
       ↓ consumes execution plan; performs provider call
       ✗ must not call back into Orchestration or Contract
```

## 9. Non-goals

- No separate `op-zeroclaw` crate.
- No independent `op-llm` authority after migration.
- No duplicate LLM provider trait in `op-chat`.
- No direct live-state file authority from `/dev/shm`.
- No SQLite plugin catalog.
- No new MCP shim service.
- No `compact-mcp` external exposure.
- No static hardcoded model picker (`match effort { ... }`).
- No execution of undeclared models/routes/tools.
