# Spec — zeroclaw-absorbs-op-llm

---

## 1. Overview

Zeroclaw is the dynamic umbrella for all LLM execution: provider catalog,
route resolution, model selection, tool-call translation, execution
authorization, and MCP/UI/gRPC exposure. This spec governs absorbing
`crates/op-llm` into Zeroclaw's plugin/schema/D-Bus architecture and retiring
`op-llm` as an independent crate.

**Primary authority file:**
`crates/op-plugins/src/state_plugins/zeroclaw.rs`

**Schema types (contract layer):**
`crates/op-plugins/src/state_plugins/common/llm_projection.rs`

**Schema re-export / `PluginSchema` builder:**
`crates/op-plugins/src/state_plugins/plugin_schema_defs.rs`

**Single projection authority (producer):**
`crates/op-projection` → `SchemaEngine`

**D-Bus object tree (view, generated by the bridge):**
`/org/opdbus/v1/plugins/zeroclaw` and children, on bus `org.opdbus.v1`

### 1.1 One projection — non-negotiable

There is **exactly one** projection of Zeroclaw, and it is owned by
`op-projection::SchemaEngine`. The Zeroclaw `PluginSchema` (derived from
`ZeroclawState`) is the single source of truth. Everything else is a **view**
derived from that one schema, never a second computation:

- The **D-Bus object tree** under `/org/opdbus/v1/plugins/zeroclaw/...` is a
  live view materialized by `op-grpc-bridge` directly from the in-memory
  `PluginSchema` held by `SchemaEngine` (§9). This is the primary call surface.
- The **`/dev/shm/opdbus/schemas/zeroclaw.json`** file is a **non-authoritative
  discovery snapshot** written by `SchemaEngine` for human/tooling inspection.
  It is **never read back** to build the D-Bus tree, and **never** used for
  execution-path decisions (§7).
- The **gRPC stream** (`ZeroclawProjection`) is a serialized view of the same
  `PluginSchema`, for remote subscribers (§9.4).

No component computes, mutates, or re-derives the projection except
`SchemaEngine`. The bridge, the file, and the gRPC stream are read-only views.

### 1.2 schemars is mandatory and is the sole schema generator

Every struct that touches the Zeroclaw schema surface — `ZeroclawState`,
`LlmProjection`, `ModelRoute`, `Provider`, `Router`, `SelectorPolicy`,
`SelectionInput`, `SelectionOutput`, `SelectionEvent`, `ZeroclawError`,
absorbed provider adapter config structs — MUST derive
`schemars::JsonSchema`. This is not optional.

The Zeroclaw `PluginSchema` field set is generated **entirely** from the
`schemars` output for `ZeroclawState` via the converter defined in §8. The
legacy `schema_from_state()` JSON-introspection path is **replaced** for
Zeroclaw. D-Bus method shapes, gRPC proto field names, MCP tool parameter
schemas, and UI field renderers all derive from this one `schemars`-generated
JSON Schema. Any struct without `#[derive(schemars::JsonSchema)]` is invisible
to the system and cannot participate in the D-Bus/gRPC/MCP surface.

## 4. Dynamic Model Selection Implementation

Location: new module
`crates/op-plugins/src/state_plugins/common/selector.rs`

```rust
pub fn select_model(
    input: &SelectionInput,
    state: &ZeroclawState,
) -> Result<SelectionOutput, ZeroclawError>
```

- Reads `state.projection.model_routes` and `state.projection.tools`.
- Reads `state.selector_policy` for weights.
- Phase 1 hard filters then Phase 2 scoring per design.md §4.
- Cost filter/scoring use the Zeroclaw-native `cost_profile` field (budget
  class). No `cost_per_token` or unit math.
- Returns `ZeroclawError::NoCandidateAfterFiltering` (or a specific hard-filter
  error) on failure.
- Pure function — no I/O, no env reads, deterministic given state.

## 5. Layer Boundaries

Two bad outcomes this spec explicitly prevents:
1. `op-llm` survives as a hidden authority under a new name.
2. `op-plugins` becomes a runtime blob mixing provider HTTP clients with schema authority.

### Layer 1 — Zeroclaw Contract Layer
`crates/op-plugins/src/state_plugins/{zeroclaw.rs, common/llm_projection.rs, plugin_schema_defs.rs}`

Owns: `ZeroclawState` and all schema types, the `schemars`-generated
`PluginSchema`, route/provider/selector declarations, OSCAL subids.
The schema IS the plugin; `PluginSchema` is the single source of truth.
Must NOT contain: provider HTTP clients, network adapters, wire-format parsing,
auth header construction, or D-Bus object registration.

### Layer 2 — Zeroclaw Orchestration Layer
`common/selector.rs` + D-Bus method handlers in `zeroclaw.rs`.

Owns: dynamic model selection, scoring, route resolution, execution
authorization, fallback planning, `MutationEngine` integration, trace/event
emission, handoff to provider adapters. Reads contract/state only through
`SchemaEngine`/`MutationEngine`/the projection. Does NOT implement wire formats.

### Layer 3 — Provider Adapter Layer
Execution-host module confirmed by the Provider Absorption spike (NOT inside the
`op-plugins` schema authority if that would mix runtime I/O with schema
ownership).

Owns: OpenAI / Anthropic / Gemini / OpenClaw / Factory / Kilocode / Opencode /
OpenRouter / GCloudADC wire formats, request/response conversion, streaming, auth
headers, network calls.

Hard constraints: cannot select models, mutate routes, read live state, bypass
D-Bus, or execute undeclared routes. Takes only a schema-authorized execution
plan. Must not call back into Orchestration/Contract, read `/dev/shm`, or query
D-Bus for live state.

### Dependency direction (see §10 for crate-level rules)
```
Contract Layer   → defines schema; schemars generates PluginSchema
Orchestration    → consumes contract/state; produces execution plan
Provider Adapter → consumes execution plan; performs provider call
                   ✗ must not call back into Orchestration or Contract
```

## 7. Single Projection Contract (`/dev/shm` is a snapshot, not an authority)

`SchemaEngine` (in `op-projection`) is the **sole writer** of any Zeroclaw
projection artifact and the **sole owner** of the in-memory `PluginSchema`.

### Lifecycle
1. `SchemaEngine` registers/holds the Zeroclaw `PluginSchema`
   (generated from `schemars` per §8).
2. On schema/state change, `SchemaEngine`:
   a. notifies registered **projection observers** (§9) — the in-memory
      `PluginSchema` is passed by reference; this is how the D-Bus tree updates;
   b. writes the discovery snapshot `/dev/shm/opdbus/schemas/zeroclaw.json`
      atomically (`.tmp` + `rename`);
   c. updates the aggregated `/dev/shm/live-schema.json` (and the catalog-hash
      manifest) in its existing aggregation pass.
3. Individual plugins NEVER write any `/dev/shm` file.

### Read path — strict
- The grpc-bridge builds the D-Bus tree from the **in-memory `PluginSchema`**
  passed by `SchemaEngine` to the observer — **never** by reading the
  `/dev/shm` JSON file.
- `op-chat` and MCP MUST use D-Bus for execution-path decisions.
- The `/dev/shm/opdbus/schemas/zeroclaw.json` file is for discovery/inspection
  only. No consumer reads it on an execution path; no consumer writes it.

### Invariants
- Snapshot file absent → SchemaEngine hasn't registered Zeroclaw yet; the D-Bus
  tree is likewise absent; callers wait.
- Snapshot stale (mtime > 30 s) → log warning; it is non-authoritative anyway.

## 8. Schemars → `PluginSchema` Generation (replaces `schema_from_state` for Zeroclaw)

The Zeroclaw `PluginSchema` is generated from `schemars`, not from JSON
introspection. Add to `plugin_schema_defs.rs`:

```rust
/// Convert a schemars RootSchema for a `#[derive(JsonSchema)]` type into the
/// runtime `PluginSchema` field set. Single generator for schema-contract types.
pub(crate) fn plugin_schema_from_schemars<T: schemars::JsonSchema>(
    name: &str,
    category: &str,
    version: &str,
    description: &str,
    methods: HashMap<String, MethodDecl>,
    signals: Vec<SignalDecl>,
    guarantees: PluginCapabilities,
    subids: HashMap<String, String>,
) -> PluginSchema;
```

- Internally calls `schemars::schema_for!(T)` and maps each top-level property
  in the generated JSON Schema to a `FieldSchema` (type, required, default,
  description), building the `PluginSchema` via `PluginSchemaBuilder`.
- `zeroclaw_plugin_schema()` is rewritten to call
  `plugin_schema_from_schemars::<ZeroclawState>(...)` and supplies the declared
  `methods` (§3), `signals`, `guarantees`, and the `subids` map (§13).
- `schema_from_state()` remains for other plugins not yet migrated; it is **not**
  used for Zeroclaw.
- A `#[test]` asserts `schemars::schema_for!(ZeroclawState)` contains
  `model_routes`, `providers`, `selector_policy`, `selection_input` (via method
  shapes), and `selection_output`, and that the produced `PluginSchema.fields`
  matches the schemars property set.

## 9. D-Bus Projection ↔ gRPC-Bridge Integration (the single call surface)

The grpc-bridge publishes the **one** Zeroclaw `PluginSchema` as a live D-Bus
object tree. It owns no projection of its own — it is an observer/view of
`SchemaEngine`. This is the primary call surface for Refactro and any
schema-driven consumer. HTTP/env reads for live execution state are prohibited.

### 9.1 Object tree

| D-Bus path | Contents | busctl example |
|---|---|---|
| `/org/opdbus/v1/plugins/zeroclaw` | `ZeroclawState` snapshot + methods | `busctl call org.opdbus.v1 /org/opdbus/v1/plugins/zeroclaw org.opdbus.v1 GetState` |
| `/org/opdbus/v1/plugins/zeroclaw/routes/<hint>` | one `ModelRoute` | `busctl introspect org.opdbus.v1 /org/opdbus/v1/plugins/zeroclaw/routes/<hint>` |
| `/org/opdbus/v1/plugins/zeroclaw/providers/<id>` | one `Provider` | `busctl introspect org.opdbus.v1 /org/opdbus/v1/plugins/zeroclaw/providers/<id>` |

`<hint>` is `ModelRoute.hint`; `<id>` is `Provider.id`.

### 9.2 Dependency direction — no cycle

`SchemaEngine` lives in `op-projection`; the bridge hook lives in
`op-grpc-bridge`. To avoid `op-projection → op-grpc-bridge → op-projection`:

- `op-projection` defines a trait (no new deps):
  ```rust
  pub trait SchemaProjectionObserver: Send + Sync {
      fn on_zeroclaw_projection(&self, schema: &PluginSchema, state: &ZeroclawState);
  }
  ```
  `SchemaEngine` holds `Vec<Arc<dyn SchemaProjectionObserver>>` and invokes them
  after each projection cycle.
- `op-grpc-bridge` depends on `op-projection` (one direction only) and provides
  `GrpcBridgeProjectionHook: SchemaProjectionObserver`. At startup the bridge
  registers its hook with `SchemaEngine::register_projection_observer(...)`.
- `op-projection` has **no** compile-time dependency on `op-grpc-bridge`.

### 9.3 `GrpcBridgeProjectionHook`
New type in `crates/op-grpc-bridge/src/zeroclaw_projection.rs`:

```rust
pub struct GrpcBridgeProjectionHook {
    connection: zbus::Connection,
    // holds the last registered object set for diffing
}

impl SchemaProjectionObserver for GrpcBridgeProjectionHook {
    fn on_zeroclaw_projection(&self, schema: &PluginSchema, state: &ZeroclawState) { /* spawn apply */ }
}

impl GrpcBridgeProjectionHook {
    pub async fn apply_projection(&self, state: &ZeroclawState) -> anyhow::Result<()>;
}
```

- Reads `state.projection.model_routes` and `.providers` from the **in-memory**
  state handed in by the observer call — never from `/dev/shm`, env, or any
  other source.
- For each route/provider, registers a D-Bus object whose **property names and
  types are enumerated from `schemars::schema_for!(ModelRoute)` /
  `schema_for!(Provider)`** — not hardcoded strings.
- Diffs against the previous cycle: unregisters objects whose `hint`/`id` no
  longer appears.
- Registration failures (e.g. bus name not yet acquired) log a warning and retry
  on the next cycle; they never abort the SchemaEngine cycle.

### 9.4 gRPC streaming
`op-grpc-bridge`'s `SchemaPassthroughService` serves the same `PluginSchema`
view over `operation.v1.PluginService` as a `ZeroclawProjection` message
(`schema_json`, repeated `ModelRouteProto`, repeated `ProviderProto`) so remote
consumers (e.g. `cognitive-mcp` on WireGuard) subscribe without polling D-Bus.
This is a serialization of the same one schema, not a new projection.

### 9.5 Non-goals
- Refactro MUST NOT call `op-llm` HTTP endpoints directly.
- Refactro MUST NOT read `/dev/shm/opdbus/schemas/zeroclaw.json` as live state;
  it uses D-Bus (§9.1) or the gRPC stream (§9.4).
- The grpc-bridge does NOT own model selection — it only projects what
  `SchemaEngine` registered. Selection flows through D-Bus `SelectModel` /
  `AuthorizeExecution` on the top-level plugin object.

## 10. Crate Dependency Direction (cycle prevention)

| Edge | Allowed? | Why |
|---|---|---|
| `op-grpc-bridge` → `op-projection` | ✅ | bridge observes SchemaEngine |
| `op-projection` → `op-grpc-bridge` | ❌ | would create a cycle; use the observer trait (§9.2) |
| `op-grpc-bridge` → `op-plugins` | ✅ | bridge reads `ZeroclawState`/schema types |
| `op-plugins` → `op-grpc-bridge` | ❌ | schema authority must not depend on the bridge |
| `op-plugins` (schema) → provider HTTP adapters | ❌ | Layer-1 must not own runtime I/O (§5) |

The observer trait and `ZeroclawState`/`PluginSchema` types are the only shared
surface across these crates.

## 13. OSCAL Subid Mechanism + Registry

### 13.1 Mechanism (reconciled with the codebase)

The **single authority** for a subid is the `PluginSchema.subids:
HashMap<String, String>` map, keyed by field / method / signal name. This is the
existing codebase convention and what the registry, renderer, and compliance
overlays read. Zeroclaw's `subids` map is supplied to
`plugin_schema_from_schemars` (§8) and is the place a reviewer/tool reads to
verify coverage and uniqueness.

`schemars` field-level extension annotations (`x-oscal-subid`) are **not** used
(schemars 0.8 cannot emit arbitrary extension keys reliably). Source-level
`// subid:` doc comments on struct fields are advisory markers only; they are
**not** the authority. The Review gate (T-80) therefore checks the **generated
`PluginSchema.subids` map** for completeness and value-uniqueness, **not** raw
`x-oscal-subid` source literals.
