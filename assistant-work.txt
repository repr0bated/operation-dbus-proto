❯ describe backend ownerships you were enforcing earlier                        

● Here's the backend ownership map I was enforcing this session — each authority
  lives in exactly one place, with a hard boundary on what it does not own:

  Schema vs Mutation — the two engines (the core split)

  - op-projection::SchemaEngine = schema/catalog authority. Sole producer of the
  SHM catalog: write_schemas_to_shm() writes the per-plugin folder +
  live-schema.json cache + .manifest.json with the one catalog_hash. Does not
  route mutations or touch the sled.
  - op-grpc-bridge::MutationEngine = mutation authority. Routes all mutations
  (gRPC + D-Bus), records the Event Chain, owns the Identity Sled
  mutation_index. Does not own the schema catalog.
  - They line up 1:1 with the identity derivation terms: Blake3(wg_pubkey ‖ 
  schema_catalog_hash ‖ mutation_index ‖ source_port) — schema engine owns the
  first, mutation engine the second.

  Single source of truth

  - The catalog is written in one place (op-projection's enumerator) — no
  competing writer.
  - The catalog_hash is computed once — op-identity's 5 re-hash sites collapsed
  to one schema_bridge::schema_catalog_hash(). Everyone else reads it; nobody
  re-derives.

  Plugins

  - Each plugin owns its own schema (schemars-derived, schema-is-the-plugin). No
  aggregate schema_def authority.
  - Plugins are declarative: they own schema() + query_current_state(). They do 
  not own mutation execution (that's the MutationEngine; apply_state is a no-op
  by convention) and do not self-write SHM (the enumerator publishes).

  The tree

  - /org/opdbus/v1/plugins is the only D-Bus tree. No service or object path
  outside it — which is why I rejected a standalone CatalogService. The catalog
  is a gemma_brain projection under /plugins/gemma_brain, not a bespoke service.

  op-web

  - Transport only — thin API/gRPC surface. Handlers that read SHM bespoke or
