  /etc/opdbus/capability-grants.json has two principals. The wildcard "*" that
  my session falls under has 49 caps, all router/chat, plus coarse
  network.read/network.write. The second principal, 898fbad6ed3f…, holds exactly
  the network-plumbing set:

  cap.network.ovsdb.port.add@v1
  cap.network.ovsdb.port.list@v1
  cap.network.ovsdb.port.delete@v1
  cap.network.ovsdb.port.ensure-internal@v1
  cap.network.ovsdb.bridge.controller.set@v1 / .read@v1
  + rtnetlink link-state / mtu / ipv4-address / route / move-netns
  That's the profile for precisely this job. Which is why list_bridges gets
  through (it validates args and complains about {} vs null) while list_ports
  comes back Access denied — different capability, and the host session doesn't
  hold it.

  The gap: nothing runs as that principal. It appears only in the grants file
  and its backups, no service references it. /etc/op-dbus/host-session-uid-map
  maps only 1001=5205f22a…, so root at boot has no session at all — which is why
  the same call as root returns nothing.

  So the rovs-based attach needs one decision from you: either map uid 0 to
  898fbad6… in host-session-uid-map, or add those two port caps to the host
  session 5205f22a. Then re-materialize with op-grants-materializer once.

  Once that's settled the rest is mechanical, and the same grant covers both
  things you asked for:

  add:    zcall rovs_commands add_port    -a
  '{"bridge_name":"ovsbr0","port_name":"netmaker","interface_type":"system"}'
  remove: zcall rovs_commands remove_port -a
  '{"bridge_name":"ovsbr0","port_name":"chatbot-port"}'
  interface_type must be "system", not the schema's "internal" default —
  netmaker is an existing WireGuard device, and the current ovsdb-port helper
  already inserts it with type "system" and an mtu_request.

  For the ordering, the new service waits on ovs-vswitchd, then the plugin tree

● The search didn't turn up much directly, but the mechanism is well understood
  and worth stating plainly.

  A WireGuard interface is pure L3 — no ethernet header, which is why the port
  shows 00:00:00:00:00:00. MAC learning can't work on it because frames arriving
  from it have no source MAC to learn, and frames sent to it are ethernet
  frames a WG device can't parse. That's the 34,450 tx errors: not a
  misconfiguration, a layer mismatch.

  There are four ways out, and they're very different in cost:

  Route to it, don't bridge it. WireGuard is designed as an L3 endpoint. This is
  the boring answer and it's why almost nobody hits this.

  encap(ethernet) / decap() — OVS packet-type-aware pipelines. This is what
  CLAUDE.md refers to, and it's the only option that keeps the port on the
  bridge. It needs the bridge running a PTAP-capable pipeline, and it's the
  thing the openflow plugin can't express, which is why the flow was never
  written.

  An L2 tunnel over the WG tunnel — GRETAP or VXLAN riding inside WireGuard.
  This is the common production answer when someone genuinely needs L2 across a
  WG mesh, because it gives you real ethernet frames to bridge.

  VPP — a different dataplane with its own WireGuard plugin and native L3
  handling. It solves the mismatch by not being an L2 switch in the first place,
  but it replaces OVS rather than fixing it.

  Sources: DPKM_OVS — WireGuard integrated into OVS ports
  (https://github.com/lukehengstenberg/DPKM_OVS) · WireGuard layer 2 discussion
  (https://gist.github.com/zOrg1331/a2a7ffb3cfe3b3b821d45d6af00cb8f6) · Open
  vSwitch (https://en.wikipedia.org/wiki/Open_vSwitch) · L2 MAC learning for
  multiport bridging (https://docs.oracle.com/en/industries/communications/sd-wa
  n-edge/9.1/featuresguide/l2-mac-learning-multiport-bridging.html)
