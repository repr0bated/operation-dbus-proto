❯ # Refactored Boot Process Review                                              
                                                                                
## Scope                                                                        
                                                                                
This review ignores legacy deploy-time service/config files and treats the      
refactored Rust code as the source of truth.                                    
                                                                                
Focused requirements:                                                           
                                                                                
- `wg-quick` for `wgcf` must run very early so the interface exists before OVS  
attach.                                                                         
- `ens3` must remain a standalone host uplink managed by `systemd-networkd`,    
not enslaved to `ovsbr0`.                                                       
- `grpc-bridge` must be present on `ovsbr0`.                                    
- OVS objects already persisted in OVSDB should be brought up through native    
control paths, not `ovs-vsctl`.                                                 
- DNS and service workloads live in Incus containers; OpenClaw is part of the   
higher service layer, not the base host fabric bootstrap.                       
                                                                                
## Refactored Source Of Truth                                                   
                                                                                
- `src/main.rs`                                                                 
  - Loads plugins into `StateManager`.                                          
  - Now boots `privacy_router` automatically by default unless                  
`OP_DBUS_ENABLE_PRIVACY_ROUTER_BOOTSTRAP=false`.                                
- `crates/op-plugins/src/state_plugins/privacy_router.rs`                       
  - Owns host privacy fabric bootstrap.                                         
  - Starts `wg-quick` for `wgcf` if the interface is missing.                   
  - Attaches `wgcf` to `ovsbr0` through native OVSDB JSON-RPC.                  
  - Brings up `ovsbr0`, `ovsbr0-mgmt`, `ovsbr0-sock`, and `grpc-bridge`.        
  - Publishes system Incus containers for privacy ingress/egress.               
  - Publishes OpenFlow chain state after the base fabric is ready.              
- `crates/op-web/src/privacy_network.rs`                                        
  - Reuses the same model during user-facing provisioning.                      
- `crates/op-grpc-bridge/src/grpc_server.rs`                                    
  - Runtime inspection only; not the fabric bootstrap authority.                
                                                                                
## Required Boot Order                                                          
                                                                                
1. `op-session-bus`                                                             
2. `op-dbus`                                                                    
3. `privacy_router` bootstrap inside `op-dbus`                                  
4. `wg-quick up wgcf`                                                           
5. Verify `wgcf` exists, then attach it to `ovsbr0` through OVSDB JSON-RPC      
6. Bring up existing OVS interfaces on the bridge:                              
   - `ovsbr0`                                                                   
   - `ovsbr0-mgmt`                                                              
   - `ovsbr0-sock`                                                              
   - `grpc-bridge`                                                              
7. Apply host L3 with `systemd-networkd`                                        
   - `ens3` stays standalone and up                                             
   - management/control-plane addressing stays on the OVS internal side         
8. Reconcile Incus system containers and privacy OpenFlow policy                
9. Start higher-layer services that depend on the privacy fabric

## Remaining Architectural Notes                                                
                                                                                
- The current `privacy_router` plugin still creates missing internal OVS ports  
if absent.                                                                      
  - That is acceptable as a recovery path, but the intended steady state is     
preseeded OVSDB objects that are only brought up.

publication when explicitly enabled.                                            
  - Default flow remains state-driven and does not require that bridged path.   
- DNS/OpenClaw container ordering is not part of the base host bootstrap in     
current Rust code.                                                              
  - They should be treated as service-layer dependencies after the privacy      
fabric is healthy.

  ---
  Issues Found

  1. existing_ports snapshot stale after uplink attach (cosmetic only)

  existing_ports is fetched once at line 545, before the uplink attach at line
  562. If attach_uplink_to_bridge=true is set later, the uplink addition won't
  appear in existing_ports when the mgmt/sock/grpc checks run. This doesn't
  cause incorrect behavior today because the uplink and internal ports are
  independent objects in OVSDB—it just means the stale snapshot can't tell you
  the uplink was already attached. With the default false, this path never
  executes.

  2. Address flush on every apply (grpc-bridge, ovsbr0-mgmt)

  Lines 629 and 647 call flush_addresses unconditionally before re-adding CIDRs.
   On a running system where these ports already have the right addresses, every
   reconcile briefly removes and re-adds them. This is a brief window
  (sub-millisecond) but any listener bound to those addresses will see a
  momentary disappearance. Consider checking whether the address is already
  assigned before flushing. Not a correctness issue on first boot; matters on
  subsequent hot-restarts.

  3. wg-quick up <config_path> not wg-quick up <interface_name>

  Line 693:
  self.run_command("/usr/bin/wg-quick", &["up", config_path])

  The requirement says "wg-quick up wgcf" (interface name), but the code passes
  the config file path. Both forms work—wg-quick accepts either—and using the
  path is actually more deterministic when multiple wgcf configs could exist.
  Worth noting in case someone checks logs and sees the path form and thinks
  it's wrong.

  4. fail_mode=secure + OF probe is non-blocking

  The OF controller probe at line 663 is fire-and-warn: if the controller isn't
  up yet, the bridge will drop all traffic until flows are pushed.
  apply_openflow_system_chain runs later (step 6) and will push the system
  chain. This matches the architecture doc, but if the OF controller isn't
  reachable at all (step 6 fails), the retry loop in main.rs will re-enter
  apply_state and re-attempt. The bridge stays in fail_mode=secure with no flows
   between retries, so host traffic on ovsbr0 internal ports is dark until the
  chain lands. This is the expected behavior given fail_mode=secure, just worth
  being intentional about.

  5. 2-second settle sleep is unconditional

  Line 1187 always sleeps 2 seconds even when containers are already running and
   DNS config is a no-op. This adds 2s to every retry in the bootstrap loop. Not
   a correctness issue, but the sleep could be skipped when
  apply_incus_system_containers returns "already in sync".

  ---
  Verdict

  The implementation is architecturally correct against all five stated
  requirements. The two items worth addressing before production hardening are
  the address flush on hot-restarts (#2) and the unconditional sleep inside
  apply (#5). Everything else is either correct or cosmetic.
