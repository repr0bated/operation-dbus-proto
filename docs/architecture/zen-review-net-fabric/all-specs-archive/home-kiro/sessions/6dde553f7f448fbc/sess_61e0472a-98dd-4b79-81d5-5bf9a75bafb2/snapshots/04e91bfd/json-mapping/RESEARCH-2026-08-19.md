# Generative UI Research — 2026-08-19

## Architecture Summary

The LLM-generated UI stack has three layers with strict responsibility separation:

| Layer | Tool | Responsibility |
|-------|------|----------------|
| **Semantic** | LLM + json-render catalog | WHAT components, WHAT data binds to them |
| **Spatial** | GridStack.js | WHERE tiles go on screen (auto-placement, drag, resize) |
| **Render** | json-render `<Renderer>` | HOW each component draws (React, inside each grid cell) |

The LLM never calculates positions. GridStack does all the math. The LLM only says "these 5 things should be on the dashboard" — GridStack auto-places them.

## Key Tools

### json-render (Vercel)
- **Repo:** `/srv/git/json-render-upstream` (cloned)
- **Package:** `@json-render/core` + `@json-render/react` + `@json-render/shadcn`
- **What it does:** AI generates `{ root, elements }` JSON specs constrained to a Zod-typed catalog. Renderer walks the spec tree safely.
- **Key features:**
  - `defineCatalog()` — register components with Zod prop schemas
  - `catalog.prompt()` — auto-generates LLM system prompt from catalog
  - `$state` / `$cond` / `$template` / `$bindState` — dynamic prop expressions
  - `visible` — conditional element rendering
  - `watch` — state-reactive actions
  - `createSpecStreamCompiler` — progressive render during LLM streaming
  - `@json-render/zustand` — state store adapter
  - `@json-render/mcp` — MCP integration
  - `@json-render/devtools-react` — inspector panel

### @dnd-kit (Vercel's choice for json-render dashboard)
- **Package:** `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`
- **What it does:** Drag-and-drop with spatial math (transforms, collision detection, sorting strategies)
- **Why this one:** It's what the official json-render dashboard example uses
- **Key features:**
  - `rectSortingStrategy` — handles grid tile reordering
  - `useSortable` hook — per-widget drag handle
  - CSS transforms (no layout recalculation)
  - Persist reordered widget IDs to backend
  - CSS Grid does the responsive columns; @dnd-kit does the drag math
  - The LLM never touches position — only generates the spec inside each tile

### GridStack.js (alternative — heavier, more Grafana-like)
- **Repo:** `/srv/git/gridstack` (cloned)
- **Package:** `gridstack`
- **What it does:** Full drag + resize grid with auto-placement and serialization
- **When to use:** If you need resize handles, variable tile sizes, and Grafana-style dashboards
- **Key features:**
  - Auto-placement algorithm (no manual x/y needed)
  - `grid.save()` / `grid.load()` for layout persistence
  - React/Vue/Angular wrappers included
  - Collision detection, responsive breakpoints

### Vercel AI SDK v5
- **Package:** `ai` + `@ai-sdk/openai` (or any provider)
- **What it does:** Multi-step inference loop with tool calling
- **Key pattern:**
  ```typescript
  const result = await generateText({
    model: provider("model"),
    prompt: "make this data accessible",
    tools: { listPlugins, getSchema, getState, searchFields },
    stopWhen: stepCountIs(N),
  });
  ```
- The LLM gets tools to explore data autonomously and outputs specs

## The Principle: Don't Have the LLM Do the Mathematics

From Builder.io research (2026):

> "Your job shifts to building perfect components while defining auto-layout
> constraints and spatial guardrails so the component looks stunning no matter
> how a chaotic AI decides to stack them together."

The LLM is a "chaotic user" of the design system. It has zero spatial intuition.
The guardrails are:
1. **Catalog** (json-render) — constrains WHAT components exist
2. **Grid engine** (GridStack) — constrains WHERE things can go
3. **Layout rules** (CSS/responsive config) — constrains HOW things resize

The LLM's entire job is semantic: pick components, bind data, describe intent.
The deterministic engines handle all spatial math.

## Separation of Concerns (Production Architecture)

```
┌─────────────────────────────────────────────────────────────┐
│  D-Bus Projected Tree (Rust backend)                        │
│  - Plugin state as individually addressable properties      │
│  - PropertiesChanged signals for live updates               │
│  - Each field is a streamable datum                         │
└───────────────┬─────────────────────────────────────────────┘
                │ WebSocket / SSE
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Zustand State Store (@json-render/zustand)                 │
│  - D-Bus state → JSON paths                                │
│  - $state expressions resolve here                          │
│  - Live updates push from backend                           │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  GridStack.js (Layout Engine)                               │
│  - Auto-places tiles from LLM spec                          │
│  - User drag/resize → serialize → persist positions         │
│  - Handles collision, responsive, mobile                    │
│  - Never touched by LLM — pure spatial math                 │
└───────────────┬─────────────────────────────────────────────┘
                │ Each tile contains:
                ▼
┌─────────────────────────────────────────────────────────────┐
│  json-render <Renderer> (per tile)                          │
│  - Walks spec tree for that tile's content                  │
│  - Atomic components: Metric, StatusLine, Label, Button...  │
│  - $state binds to zustand paths (= D-Bus properties)       │
│  - Rendered scrollbars, not native browser overflow         │
└─────────────────────────────────────────────────────────────┘
```

## How the LLM Generates

1. `catalog.prompt()` gives the LLM the full component catalog as system context
2. Plugin schemas (from sealed blobs) give it the data surface
3. The prompt is: "make this data as accessible as possible"
4. The LLM does NOT know it's building a UI
5. It outputs `{ root, elements }` specs — flat JSON, one element per line
6. Each element: `{ type: "Metric", props: { label: "Memory", value: { "$state": "/procfs/memory/MemTotal" } } }`
7. Bind paths work with or without leading `/` (interpreter normalizes)
8. GridStack auto-places; user rearranges; positions persist

---

## Catalog vs Gallery

- **Catalog** = the active rendered dashboard (composed by LLM, positioned by GridStack)
- **Gallery** = bench of unused/new components (last menu item, with promote button)
- LLM novelty specs land in gallery first
- User promotes from gallery → catalog (active dashboard)
- LLM can retire unused components: catalog → gallery
- Over time: refine, retire unused, recognize new components

## Critical Design Decisions

1. **json-render used as-is** — no reimplementation, no Rust interpreter replacement
2. **One TypeScript shell file** — `main.tsx` mounts the renderer, nothing else
3. **D-Bus first for state** — backend pushes to zustand via websocket
4. **GridStack for layout math** — LLM never touches coordinates
5. **Components are atomic** — one component, one datum, one line in the spec
6. **Slash-agnostic binds** — `"status"` and `"/status"` both work (normalizer)
7. **LLM is autonomous** — no user trigger, adapts on runtime state changes
8. **Rendered scrollbars** — no native browser overflow, all custom
9. **`catalog.prompt()`** — auto-generated system prompt, not hand-written
10. **Streaming** — `createSpecStreamCompiler` for progressive render during generation
