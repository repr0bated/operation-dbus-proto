# Generative UI Research — 2026-08-19

## Architecture Summary

The LLM-generated UI stack has three layers with strict responsibility separation:

| Layer | Tool | Responsibility |
|-------|------|----------------|
| **Semantic** | LLM + json-render catalog | WHAT components, WHAT data binds to them |
| **Spatial** | GridStack.js | WHERE tiles go on screen (auto-placement, drag, resize) |
| **Render** | json-render `<Renderer>` | HOW each component draws (React, inside each grid cell) |

The LLM never calculates positions. GridStack does all the math. The LLM only says "these 5 things should be on the dashboard" — GridStack auto-places them.

## Key Tools

### json-render (Vercel)
- **Repo:** `/srv/git/json-render-upstream` (cloned)
- **Package:** `@json-render/core` + `@json-render/react` + `@json-render/shadcn`
- **What it does:** AI generates `{ root, elements }` JSON specs constrained to a Zod-typed catalog. Renderer walks the spec tree safely.
- **Key features:**
  - `defineCatalog()` — register components with Zod prop schemas
  - `catalog.prompt()` — auto-generates LLM system prompt from catalog
  - `$state` / `$cond` / `$template` / `$bindState` — dynamic prop expressions
  - `visible` — conditional element rendering
  - `watch` — state-reactive actions
  - `createSpecStreamCompiler` — progressive render during LLM streaming
  - `@json-render/zustand` — state store adapter
  - `@json-render/mcp` — MCP integration
  - `@json-render/devtools-react` — inspector panel

### @dnd-kit (Vercel's choice for json-render dashboard)
- **Package:** `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`
- **What it does:** Drag-and-drop with spatial math (transforms, collision detection, sorting strategies)
- **Why this one:** It's what the official json-render dashboard example uses
- **Key features:**
  - `rectSortingStrategy` — handles grid tile reordering
  - `useSortable` hook — per-widget drag handle
  - CSS transforms (no layout recalculation)
  - Persist reordered widget IDs to backend
  - CSS Grid does the responsive columns; @dnd-kit does the drag math
  - The LLM never touches position — only generates the spec inside each tile

### GridStack.js (alternative — heavier, more Grafana-like)
- **Repo:** `/srv/git/gridstack` (cloned)
- **Package:** `gridstack`
- **What it does:** Full drag + resize grid with auto-placement and serialization
- **When to use:** If you need resize handles, variable tile sizes, and Grafana-style dashboards
- **Key features:**
  - Auto-placement algorithm (no manual x/y needed)
  - `grid.save()` / `grid.load()` for layout persistence
  - React/Vue/Angular wrappers included
  - Collision detection, responsive breakpoints

### Vercel AI SDK v5
- **Package:** `ai` + `@ai-sdk/openai` (or any provider)
- **What it does:** Multi-step inference loop with tool calling
- **Key pattern:**
  ```typescript
  const result = await generateText({
    model: provider("model"),
    prompt: "make this data accessible",
    tools: { listPlugins, getSchema, getState, searchFields },
    stopWhen: stepCountIs(N),
  });
  ```
- The LLM gets tools to explore data autonomously and outputs specs

## The Principle: Don't Have the LLM Do the Mathematics

From Builder.io research (2026):

> "Your job shifts to building perfect components while defining auto-layout
> constraints and spatial guardrails so the component looks stunning no matter
> how a chaotic AI decides to stack them together."

The LLM is a "chaotic user" of the design system. It has zero spatial intuition.
The guardrails are:
1. **Catalog** (json-render) — constrains WHAT components exist
2. **Grid engine** (GridStack) — constrains WHERE things can go
3. **Layout rules** (CSS/responsive config) — constrains HOW things resize

The LLM's entire job is semantic: pick components, bind data, describe intent.
The deterministic engines handle all spatial math.

                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  GridStack.js (Layout Engine)                               │

## How the LLM Generates

1. `catalog.prompt()` gives the LLM the full component catalog as system context
2. Plugin schemas (from sealed blobs) give it the data surface
3. The prompt is: "make this data as accessible as possible"
4. The LLM does NOT know it's building a UI
5. It outputs `{ root, elements }` specs — flat JSON, one element per line
6. Each element: `{ type: "Metric", props: { label: "Memory", value: { "$state": "/procfs/memory/MemTotal" } } }`
7. Bind paths work with or without leading `/` (interpreter normalizes)
8. GridStack auto-places; user rearranges; positions persist

---

## Catalog vs Gallery

- **Catalog** = the active rendered dashboard (composed by LLM, positioned by GridStack)
- **Gallery** = bench of unused/new components (last menu item, with promote button)
- LLM novelty specs land in gallery first
- User promotes from gallery → catalog (active dashboard)
- LLM can retire unused components: catalog → gallery
- Over time: refine, retire unused, recognize new components

## Critical Design Decisions

1. **json-render used as-is** — no reimplementation, no Rust interpreter replacement
2. **One TypeScript shell file** — `main.tsx` mounts the renderer, nothing else
3. **D-Bus first for state** — backend pushes to zustand via websocket
4. **GridStack for layout math** — LLM never touches coordinates
5. **Components are atomic** — one component, one datum, one line in the spec
6. **Slash-agnostic binds** — `"status"` and `"/status"` both work (normalizer)
7. **LLM is autonomous** — no user trigger, adapts on runtime state changes
8. **Rendered scrollbars** — no native browser overflow, all custom
9. **`catalog.prompt()`** — auto-generated system prompt, not hand-written
10. **Streaming** — `createSpecStreamCompiler` for progressive render during generation

## Data Processing, Display, and Per-Datum UI Interaction

### The Pattern: Every Data Point Gets Action Affordances

The core idea: each datum rendered in the UI isn't just a display — it's an interactive unit with actions the user can take on that specific data point.

In json-render terms:

```json
{
  "type": "Metric",
  "props": {
    "label": "Memory Total",
    "value": { "$state": "/procfs/memory/MemTotal" },
    "format": "number"
  },
  "on": {
    "press": { "action": "drillDown", "params": { "path": "/procfs/memory" } }
  }
}
```

Every rendered element can have an `on` field that maps events to actions. The action carries the data context (which plugin, which field, which path).

### How json-render Actions Work

From the json-render source (Issue #99 + README):

1. **Catalog defines available actions** with typed params (Zod schema)
2. **Elements bind events to actions** via the `on` field
3. **Components emit events** by name (`emit("press")`)
4. **The renderer maps the event** to the action + params from the spec
5. **ActionProvider handlers execute** the action (call D-Bus method, navigate, drill-down)

```typescript
// Catalog: define what actions exist
actions: {
  callMethod: {
    description: "Call a D-Bus method on a plugin",
    params: z.object({
      pluginId: z.string(),
      method: z.string(),
      args: z.record(z.any()).optional(),
    }),
  },
  drillDown: {
    description: "Navigate to detail view for a data point",
    params: z.object({ path: z.string() }),
  },
  setState: {
    description: "Update local UI state",
    params: z.object({ statePath: z.string(), value: z.any() }),
  },
}

// Handler: what happens when actions fire
const handlers = {
  callMethod: async ({ pluginId, method, args }) => {
    // Route through gRPC → MutationEngine → D-Bus
    await grpcClient.callMethod(pluginId, method, args);
  },
  drillDown: ({ path }) => {
    // Update state to show detail view for this path
    store.setState({ activeDrillDown: path });
  },
};
```

### The Data Processing Pipeline

```
D-Bus mutation (Rust backend)
    ↓ PropertiesChanged signal
Write projection to SHM (/dev/shm/opdbus/state/<plugin>.json)
    ↓ WebSocket push to frontend
Zustand store update (keyed by JSON pointer path)
    ↓ $state expression resolution
json-render re-renders affected elements
    ↓ User interacts (click, press)
Action fires → handler → gRPC → MutationEngine → D-Bus method call
    ↓ Round-trip: new state flows back through the same pipeline
```

### Per-Item Interactivity in Collections (repeat + actions)

Inside a `repeat` (the child collection rendering), each item gets its own action context:

```json
{
  "kind": "repeat",
  "bind": "/state/mutations/items",
  "child": {
    "type": "Stack",
    "props": { "dir": "h" },
    "children": ["label-op", "pill-status", "btn-retry"],
    "elements": {
      "label-op": { "type": "Label", "props": { "text": { "$state": "operation" } } },
      "pill-status": { "type": "StatusPill", "props": { "value": { "$state": "status" } } },
      "btn-retry": {
        "type": "Button",
        "props": { "label": "Retry" },
        "on": {
          "press": {
            "action": "callMethod",
            "params": {
              "pluginId": { "$state": "/pluginId" },
              "method": "retry_mutation",
              "args": { "mutation_id": { "$state": "id" } }
            }
          }
        }
      }
    }
  }
}
```

Each row's Retry button carries that row's `id` in the action params. The `$state` expression resolves relative to the item — so each button targets its own mutation.

### Types of Per-Datum UI Interactions

| Interaction | json-render mechanism | Backend handler |
|-------------|----------------------|-----------------|
| Drill-down to detail | `on: { press: { action: "drillDown" } }` | setState → show detail panel |
| Retry/restart operation | `on: { press: { action: "callMethod" } }` | gRPC → MutationEngine → D-Bus |
| Toggle enable/disable | `$bindState` on a Switch component | setState → callMethod on change |
| Delete/remove | `on: { press: { action: "callMethod", method: "remove" } }` | gRPC → MutationEngine |
| Copy value to clipboard | `on: { press: { action: "copyToClipboard" } }` | Client-side handler |
| Open in context (smart button) | `on: { press: { action: "navigate", params: { ref } } }` | Router navigate to referenced object |
| Inline edit | `$bindState` + `watch` for commit | Two-way binding → callMethod on blur/enter |

### Smart Buttons (OpenFlow Log Example)

Your earlier idea about OpenFlow logs with buttons that take you to whatever is referenced:

```json
{
  "type": "LogEntry",
  "props": {
    "message": { "$state": "message" },
    "timestamp": { "$state": "timestamp" }
  },
  "on": {
    "press": {
      "action": "navigate",
      "params": {
        "target": { "$state": "referenced_object_path" }
      }
    }
  }
}
```

Each log line carries its referenced object path. Click → navigate to that object's detail view. The LLM doesn't hardcode navigation — it binds the action to the data, and the data carries the reference.

### CQRS Alignment

This maps directly to your architecture's CQRS pattern:

- **Command side:** Actions → `callMethod` → gRPC → MutationEngine → Event Chain → D-Bus
- **Query side:** SHM projections → WebSocket → Zustand → `$state` → Renderer
- **Projection:** The sealed blob is the read model. Mutations update it. The UI reads from it.
- **Event sourcing:** Every mutation is a chain event. The UI shows the projection, not the event log.

The UI never writes directly to state. Every interaction is an action that routes through the single gated mutation door (MutationEngine). The response flows back as a state change through the same projection pipeline.

### Key Insight: Actions Are Data Too

The available actions for each data point should be part of the data model, not hard-coded in the UI:

```json
{
  "id": "019…",
  "operation": "configure",
  "status": "applied",
  "actions": ["view", "retry", "rollback"]
}
```

The LLM sees `actions: ["view", "retry", "rollback"]` in the schema and generates buttons for each. If a mutation's status changes to "failed", the backend adds "retry" to its actions array. The UI adapts without regeneration — it's just state.

This is what the lightning model proposed:
> Put a compact, render-oriented index in the collection payload... `"actions": ["view", "retry"]`
