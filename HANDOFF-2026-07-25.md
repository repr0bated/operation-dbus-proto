- Every main service kept its PID — only loggers respawned. Rotated history intact.

**Two traps, both cost time:**
- `sv restart <svc>/log` does **not** cycle a logger — svlogd blocks reading the
  still-open pipe and sits in `got TERM`. Use **`sv force-restart`**. It is safe:
  `runsv` (not the service) owns the log pipe, so killing the logger cannot
  SIGPIPE the producer. Verified across 31 restarts.
- `usermod -l` refuses to rename an account with live processes. Create the new
  user, rewrite scripts, chown, force-restart loggers onto it, then `userdel`.

## 2. Uncommitted in the tree — OSCAL subid work

**The CI gate `default_registry::tests::all_plugin_subids_are_valid_and_unique`
was already FAILING on a clean tree** (13 failures) and is now **green**.

Failures were: 5 subids the regex rejected outright (`fail2ban` `sch.security.*`,
`persona` ×4 `*.agent.*`), and 8 from `mut.*`/`src.*` subids declared with none of
the accountability fields they oblige — `blockchain`, `json_render`,
`openflow_obfuscation`, `wg_opdbus` were declaring **mutations and authoritative
source reads with no `actor_id`/`capability_id`/`source_system`/`source_locator`
at all**. That is the property those categories exist to enforce; it went unnoticed
because a permanently red gate stops being read.

### Files changed
- **`common/oscal.rs`** — three vocabularies:
  - `OSCAL_COMPONENT_TYPES` — mirrors the standard, **do not extend**
  - `INTERNAL_CATEGORIES` — `agent`/`data`/`security`/`storage`; extend freely;
    `canonical_category` returns them **as-is** (forcing them into an OSCAL noun
    would be a false claim in a compliance artifact)
  - `CATEGORY_ALIASES` — `ui`→`software`, `llm`→`service`, `agents`→`software`;
    readable term survives in the subid, resolves to conformant OSCAL on export
  - **`subid_regex()` is now BUILT from those lists** instead of a hand-typed
    string. That drift is precisely why `storage` was rejected while btrfs emitted it.
- **`plugin_scaffold_helpers.rs`** — `derive_schema_subid(name, declared_category, declared)`.
  Declared `x-oscal-category` wins (the one fact not derivable); else inferred from
  the plugin's own field subids; kebab-cased (grammar forbids underscores);
  deterministic sort **because the value feeds the schema hash**. An unusable
  declared category is ignored, not emitted.
- **`schemars_adapter.rs`** — reads struct-level `x-oscal-category`; derives
  `__schema__` when absent; calls `ensure_category_metadata_fields` so declaring a
  `mut.*`/`src.*`/`evt.*` subid automatically carries its required fields.
- **`oscal_subid_registry.rs`** — `SUBID_REGEX` const → `subid_regex()`.
- **`op-state-store/src/plugin_schema.rs`** — only `SCHEMA_SUBID_KEY` added.

10 unit tests cover derivation, aliases, determinism, and the alias table itself
(one test asserts every alias resolves to a real OSCAL category — a typo there
would silently emit non-conformant output).

### ⚠️ Trap: do NOT put the derivation in `PluginSchemaBuilder::build()`
First attempt did; it is **inert**. `plugin_schema_from_json` calls `.build()` on an
empty builder and then does `schema.subids = subids` — a wholesale overwrite — and
each plugin attaches its methods only *after* the adapter returns. **No `build()`
call ever sees a complete schema.** Deleting the per-plugin struct attributes on
that assumption would have dropped `__schema__` for 40 plugins.

### In flight when the session ended
A worker was removing the 21 `#[cfg(test)] *_schema_golden()` functions and their
`derived_schema_matches_hand_rolled` tests. Those were migration guards that had
begun asserting the derived schema must **not** gain the required accountability
fields. Baseline before the work: **2 already failing** (`oscal_subid_registry`,
`software`); my adapter change made it 8. **Check `cargo test -p op-plugins` is fully
green and the OSCAL gate still passes.** If the worker did not finish, the deletions
are mechanical — production (non-`cfg(test)`) schema fns and `all_subids_are_valid`
tests must be kept.

## 3. Not done — decisions needed

1. **Reseal.** Nothing sealed; catalog still at generation 380, hash `13bace01…`,
   65 plugins. Jeremy: resealing takes ~2s. Needs `opblob` rebuilt+installed first,
   since the schema changes live in the binary. On seal, 20 plugins gain a
   `__schema__` and 4 gain accountability fields → new hashes and blob filenames.
2. **DECIDED (Jeremy): hardcode the category on each plugin.** *"Why don't we just
   set the category field on the plugin — safe to hardcode that."* Correct, and the
   code already supports it: a declared category **always wins**, inference is only
   the fallback for plugins not yet updated. Hardcoding is not the duplication that
   was just removed — the full subid *string* is derivable from category + name and
   should never be pasted per plugin, but the category itself is irreducible
   per-plugin knowledge and belongs in the plugin.

   **The remaining work is therefore mechanical: write the value into every plugin.**
   Today only **10 of 65** declare any category, and 2 of those were invalid (`llm`,
   `agents` — now valid as aliases). Until then the 20 with empty subid maps default
   to `software`, including `openflow`, which should be `network` (its methods say
   so, but methods are not visible to the adapter). Subids are immutable per subject,
   so do this **before sealing** — cheaper than versioning later.

   Declare it as a struct-level `#[schemars(extend("x-oscal-category" = "network"))]`
   (what the adapter reads). The template `plugin_scaffold.rs.template` already has a
   `PLUGIN_CATEGORY` slot at line 28 — add the attribute beside it so every scaffolded
   plugin declares one and this cannot recur. Good worker task: 65 files, value drawn
   from each plugin's existing method subids where present, flagged where ambiguous.
3. **`ensure_category_metadata_fields` is not universal.** It fires inside
   `plugin_schema_from_json`, so hand-built plugins bypass it (`dnsresolver`
   confirmed). Jeremy: *"that's something we can go back and fix, it's not a
   placeholder or a stub"* — migrate them onto the derived path, do not delete.
   Alternative: call the helper at the registry aggregation point, where every
   schema converges regardless of how it was built.
4. **procfs is wrong in five ways** (unresolved):
   - read-only only — `/proc/sys` is writable and there is no `mut.*` path.
     Jeremy's direction: keep procfs RO, split the write surface out. Note
     `/proc/sys` is **procfs, not sysfs**, so name it for function (`sysctl` /
     `kernel_tunables`), not for the filesystem.
   - all 10 fields are `simd_json::Value` → `FieldType::Any` → **ten
     `google.protobuf.Value`** in `proto_gen.rs:270`. Untyped end to end.
   - `memory` (field) vs `meminfo` (method) — two subjects for one thing.
   - 5 fields have no accessor; `processes` has methods but **no field**.
   - after the RO/write split its methods are all `obs.service.*`, so its
     category resolves unambiguously.
5. **Nav / existing UI elements.** Measured: of 40 pages only **6** map to a plugin,
   4 loosely, **30 not at all** — while **~55 of 65 plugins had no page**, which
   `PluginPage` now covers. So the work is *sorting*, not converting: bespoke
   interaction surfaces (Chat, Explorer, Pairing, E-Stop) stay hand-written;
   cross-cutting views (Overview, Accountability, Orchestration) belong to the
   generated path; only the 6 exact matches are deletion candidates. Suggested
   cheap next step: diff `PluginPage`'s output for `cron` or `btrfs` against the
   hand-written page — the delta *is* the list of missing catalog primitives (the
   registry has only 8: container, card, kv, heading, text, badge, row, code — no
   table, form, action, or chart). Nav itself should be two tiers: curated
   `ui_surfaces` (zeroclaw plugin, `ListUiSurfaces`, 3 seeded entries today,
   `{path,name,schema}` — needs group/icon/order added) plus the generated plugin
   index, so the hardcoded 45-entry array in `AppShell.tsx` stops growing.
6. **Typing the hand-rolled plugins: find the upstream structured spec, don't hand-write.**
   Jeremy (2026-07-25): *"searching openapi will easily find structured versions of
   all handrolled."* This is the same move that already worked once — SIGNALS
   records the openflow types being generated from an official JSON schema
   (dancasey/openflow-schema) via schemafy and **vendored** as generated `.rs`, so
   schemafy never entered the build graph. Repeat that per plugin instead of
   authoring schemas by hand. The source splits by what backs the plugin:
   - **HTTP-API-backed** (`incus`, `netmaker`, `qdrant`, `cozo`, `mail_server`,
     `packagekit`…) → upstream **OpenAPI/Swagger** specs. Incus and Netmaker both
     publish one.
   - **D-Bus-backed** (`login1`, `freedesktop`, `users`, `keyring`,
     `systemd_networkd`…) → the structured source is **introspection XML**, not
     OpenAPI — and `crates/op-introspection` already parses D-Bus XML into
     serializable structs (`parser.rs`, `scanner.rs`). That crate is likely a
     shortcut for this whole class.
   - **procfs/sysfs** → no upstream spec exists. Jeremy's route: use an LLM with
     **structured outputs** to infer the schema from a live sample, then *"modify
     the output to your needs"* — it is a first draft you edit, not output consumed
     verbatim. This fills the one gap schemafy cannot: schemafy consumes a JSON
     Schema and will not infer one from a sample. Worked example he supplied: a
     Pydantic model (`CpuCore`/`CpuInfoParsed`) passed as `response_format`, where
     declaring `cache_size_kb: int` + "extracted as an integer in kilobytes" makes
     the model normalise `9216 KB` → `9216` with no regex, and `List[CpuCore]`
     scales to any core count.

     **Boundary — authoring time only, never runtime.** A `/proc` read on a control
     plane is constant and must stay a deterministic Rust parser (~20 lines); an LLM
     call per read is unbounded cost/latency, and on a many-core box `cpuinfo` is
     huge. Also: the snippet is Python (CLAUDE.md forbids new Python) and calls
     OpenAI `gpt-4o-mini` directly, which contradicts "models/routes/providers
     resolve through the gateway; inference is SALAD" — route it through zeroclaw if
     used. And it ships host `/proc` contents off-box, so sample from a scratch
     machine, not 188.68.58.237. Output a JSON Schema, vendor it under
     `schemas/procfs/`, feed the same schemafy path openflow used, commit the
     generated Rust — LLM at authoring time, deterministic for ever after. (API
     note: structured outputs are GA — `client.chat.completions.parse`, not `beta`.)
   Whichever route, keep the openflow convention: vendor the source schema under
   `schemas/<domain>/` and commit the generated `.rs`, no build-time codegen dep.
   Note `repos-bulk` already contains `json-schema-org__json-schema-spec`,
   `confluentinc__schema-registry`, `opencontrol__schemas` and `GREsau__schemars`.

7. **schemafy fork not found.** Stock `schemafy-cli-0.1.0`/`schemafy_lib`/`_core`
   are in the cargo registry, extracted 2026-07-24 17:59, **unmodified** (source
   mtimes are upstream). No local checkout, no `[patch.crates-io]`, not in

## 5. Gotcha worth keeping

`/api/plugin-schema/` **with an empty id returns `200 text/html`** — the SPA
fallback — which surfaces in a browser as the cryptic
`Unexpected token '<', "<!doctype "…`. The hook now guards empty ids and rejects
non-JSON content types with a message naming the cause. Any new API path that
"works" but returns HTML is this.
