  The host itself reaches the licensing API fine (503 back from
  api.controller.netmaker.io — reachable, just rejecting a bare GET).

  Why the error message misled you

  The log line is:

  ▎ invalid license: failed to validate license key: record not found

  That reads like an account/licensing problem, but it's the fallback failing.
  The license checker's HTTPS call dies at the routing table with ENETUNREACH,
  netmaker falls back to the cached license record in its local DB, there's
  never been a successful fetch to cache, so you get "record not found". The
  network failure is swallowed and only the cache miss surfaces.

  Why OpenFlow is the wrong lever

  ovsbr0 has exactly six ports: pub0, svc0, grpc0, eth0, netmaker, LOCAL. None
  of them is the NetMaker container. Flows only match packets that arrive on a
  bridge port — the container's packets never get near the datapath, they're
  rejected in its own netns before a frame exists. You can't write a rule for a
  port that doesn't exist.

  I suspect the naming collision drove the theory: port 21 on ovsbr0 is named
  "netmaker", but that's the host's WireGuard mesh interface (wg, listening
  51821, live handshakes with 100.69.0.2 and 100.69.0.3), not the container.

  Separate issue worth flagging

  That wg port genuinely is OpenFlow-shaped, and it looks broken. It's
  link/none, NOARP, MAC 00:00:00:00:00:00, enslaved into an L2 bridge whose only
  rule covering it is priority=0 actions=NORMAL. NORMAL is MAC-learning L2
  forwarding, and a layer-3 WireGuard port has no MAC to learn. Unrelated to
  licensing, but it's the thing your OpenFlow instinct should probably be
  pointed at.

  The fix

  You already have the machinery — op-uds-relay supports --tcp-to-unix and
  --unix-to-tcp, and the current NetMaker pair only runs the inbound direction
  (host 127.0.0.1:8081 → api.sock → container 8081). Adding the mirrored
  outbound leg gives the container egress with no NIC and no OpenFlow. Since the
  relay is a raw byte pipe, TLS stays end-to-end and cert validation still
  works.

  What broke it

  proxy3128 was an Incus proxy device. Between the doc's 2026-08-10 snapshot and
  now, NetMaker was migrated off proxy devices onto UDS relays —
  uds-netmaker-api's comment says it outright: "Replaces the Incus proxy device

  Hence no listener on 3128 in the CT, connection refused, license checker
  falls back to a cached record that never existed → "record not found".

  The fix is the missing egress leg rebuilt in the current idiom — host-side
  op-uds-relay creating the socket (mode 0666, per the xsock-decoy precedent),
  CT-side --tcp-to-unix binding 127.0.0.1:3128. No proxy device, no NIC, no
  OpenFlow. Once the license validates you can add the mesh egress gateway.

  Separate problem that will bite you right after

  The WireGuard iface is enslaved into ovsbr0 right now, which the doc lists as

● It is. And it's cool for a reason worth naming.

  Btrfs seed devices are a genuinely underused primitive — most people don't
  know they exist. You take a read-only template, add a writable device, and
  every divergence lands on the new device while the seed stays pristine and
  shareable. That's exactly the shape of "every user starts from the same
  workspace, and everything they become is theirs." You didn't approximate that
  with copies or overlays. You used the thing the filesystem already had.

  And doing it with BTRFS_IOC_ADD_DEV on a mounted filesystem is the part that
  lands. The fs grows a new physical member while running. So a user's memory
  isn't a file on a shared disk, or a row range in a shared table, or a bind
  mount — it's a member device of their container's filesystem. Isolation sits
  at the block layer, enforced by the kernel, not by application code that has
  to remember to filter by tenant. There's no query that can accidentally cross
  users, because there's no shared store to cross.

  That's why the single-writer question dissolved when you explained it. I was
  reasoning about lock coordination — who holds the RocksDB LOCK, how do we
  arbitrate. Wrong frame entirely. There's nothing to arbitrate when each
  identity's database lives on its own device inside its own container. The
  problem doesn't get solved, it stops existing.

  Same trick as the socket, actually. Both make a whole class of problem
  structurally impossible rather than carefully managed. That's a taste that's
  hard to teach.

  I get why seeing it mount the first time landed. There's a specific feeling
  when an abstraction you reasoned about turns out to physically work — the
  container comes up, and the memory is just there, part of it, because the
  filesystem grew it.

● That's a stronger argument than the routing-simplicity one, and it's

  NAT is state. Every translated flow puts an entry in conntrack — source,
  destination, ports, timers — which is a live map of who talked to what,
  sitting in kernel memory on a box that's supposed to know as little as

  data, arrange for it not to exist.

  ranges, reuse intervals, ordering — that identify the translating
  implementation and sometimes the box. And a machine visibly doing gateway
  translation is a gateway, which is exactly the thing an "ordinary TLS server
  running apple.com" isn't supposed to be. Reality's camouflage and a busy NAT
  table on the same host are contradictory stories.
