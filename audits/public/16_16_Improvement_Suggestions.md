1. **Unified Relational-Graph Query Storage via CozoDB for Projections and Introspection Telemetry** | **Rationale:** The workspace incorporates multiple overlapping database configurations: relational SQLite (via `sqlx-sqlite` and `rusqlite`) and graph-vector relational CozoDB (using the `storage-sled` backend). Storing high-frequency D-Bus object hierarchies, introspection mirror states, and system projections in standard relational tables requires complex recursive CTEs or leads to severe N+1 latency bottlenecks. Standardizing on CozoDB's datalog-based engine for telemetry representation allows querying deeply nested graph nodes and vector search states unified with relational attributes. This eliminates the maintenance, linking, and library overhead of running both standard SQLite engines and CozoDB concurrently. | **Example:** `Cargo.toml:72`

2. **Enforce Static Compile-Time Schema Validation with Protocol Buffers instead of Ad-hoc JSON-Schema Validation** | **Rationale:** The root workspace utilizes `jsonschema` for contract validation and heavily depends on `serde_json`, `simd-json`, and `serde_yaml` alongside `prost` / `tonic`. Performing dynamic contract validation at runtime using `jsonschema` for critical system control loop inputs is inefficient and introduces dynamic runtime failure points. Message flows through internal systems (`op-dbus`, `op-grpc-bridge`, etc.) should be statically defined via versioned Protocol Buffer schemas, with Rust types auto-generated at build time, enforcing schema-as-code guarantees without dynamic parsing overhead. | **Example:** `Cargo.toml:60`

3. **Leverage Zero-Copy Lifetimes and Allocation-Free Parsers in `simd-json` Deserialization across Control Plane Boundaries** | **Rationale:** High-throughput system event dispatchers (like the D-Bus control plane in `op-dbus` and the telemetry mirror in `op-dbus-mirror`) can suffer significant allocation bottlenecks from copying payloads. The workspace dependencies currently pull in `simd-json` with the generic `serde` feature enabled. Enabling borrowing-based deserialization (e.g., matching lifetime constraints on structs utilizing `borrow-or-share` or borrowing from incoming `Bytes` buffers) would eliminate costly `String` and `Vec` allocations during massive JSON telemetry ingress. | **Example:** `Cargo.toml:57`

4. **Consolidate Micro-Crates (`op-dbus-model`, `op-dbus-mirror`, `op-grpc-bridge`) to Avoid Complex Link Times and Graph Cycles** | **Rationale:** The workspace specifies over 34 separate member crates (including `op-dbus-model`, `op-dbus-mirror`, `op-introspection`, etc.). An excessive count of tightly-coupled micro-crates increases build times dramatically due to linking overhead and compiler synchronization boundaries, and introduces a risk of cyclic dependency graphs. Merging mirroring, modeling, and bridging logic into a single cohesive system-level crate (e.g., `op-dbus-core`) simplifies dependency paths and leverages LLVM's intra-crate optimization passes. | **Example:** `Cargo.toml:33`

5. **Implement Typestate Design Patterns for Stateful Keyring and Identity Initialization inside `op-identity`** | **Rationale:** The `op-identity` workspace member relies on the stateful `keyring` library. Keyring and credential loading are naturally stateful processes (e.g., `Uninitialized` -> `KeyringUnlocked` -> `IdentityConfigured`). Standard procedural APIs depend on runtime checks to ensure a key was successfully fetched, raising the potential for panic or unauthenticated routing. Transitioning to compile-time state tracking using the Typestate pattern on identity contexts ensures that operations requiring keys can only be called on an `Identity<Unlocked>` state type. | **Example:** `Cargo.toml:28`
