# Production Security & Quality Audit: op-agents

## 1. Workspace Dependency Analysis
Based on the workspace `Cargo.toml`, the following crates are defined as workspace members or dependencies. We identify which crates directly depend on `op-agents` or are designed to interact with it:

*   **op-tools**: Lists `op-agents` as a dependency in `Cargo.toml`.
*   **op-web**: Links to `op-agents` in `Cargo.toml` to serve UI routes and coordinate web-initiated agent sessions.
*   **op-chat**: Interacts with `op-agents` (conceptually referenced as the execution target for `ChatActor`'s tool loader).
*   **op-dbus**: The main control plane umbrella crate, although it does not link directly to `op-agents` in its static binary dependencies, since agents are spawned as standalone D-Bus processes (`dbus-agent` or `op-agent-manager`).

## 3. HTTP & gRPC Endpoints Exposed
The crate contains an Axum HTTP router that can be mounted into web servers such as `op-http` or `op-web`. 

### 3.1 HTTP Endpoints
All endpoints are prefixed under `/api/agents` via the `AgentsServiceRouter` metadata implementation:
*   `GET /api/agents/` — List all active agent instances (`list_agents_handler`)
*   `POST /api/agents/` — Spawn a new agent instance (`spawn_agent_handler`)
*   `GET /api/agents/health` — Retrieve agent management service health (`health_handler`)
*   `GET /api/agents/types` — List all statically compiled agent types (`list_types_handler`)
*   `GET /api/agents/:id` — Retrieve the status of a specific running agent instance (`get_agent_handler`)
*   `DELETE /api/agents/:id` — Kill/terminate a running agent instance (`kill_agent_handler`)
*   *Source*: `crates/op-agents/src/router.rs:56-65`

### 3.2 gRPC Endpoints
There are **no direct gRPC endpoints** exposed within `op-agents`. Any gRPC bridges must interface with D-Bus IPC or HTTP endpoints externally.

## 4. Flagged Integration & Circular Dependency Risks

### 4.1 Compile-Time Circular Dependency Risk with `op-http`
*   **Symptom**: `op-agents` depends directly on `op-http` in its manifest:
    ```toml
    op-http = { workspace = true }
    ```
    *(Source: `crates/op-agents/Cargo.toml:23`)*
    And it implements `op_http::router::ServiceRouter` in `crates/op-agents/src/router.rs:69`.
*   **Risk**: If `op-http` attempts to import or use any type from `op-agents` directly to pre-register routes, a compile-time circular dependency will block compilation.
*   **Mitigation**: Ensure `op-http` remains entirely generic. The main binary orchestrator (e.g., `op-web` or `op-dbus`) must import both crates and pass the router generated by `op_agents::router::create_router` to `op_http`'s server builder.

### 4.2 Decoupling via D-Bus IPC
The system architecture correctly decouples the core workspace engines (like `op-chat` and `op-web`) from direct linking dependencies on many agent types by routing tasks over D-Bus IPC. This prevents massive binary bloat and linking cycle risks.

## 5. Schema-As-Code Violations
This codebase implements a schema-as-code discipline using Protocol Buffers and OSCAL. However, several data contracts in `op-agents` bypass versioned schemas, relying on **ad-hoc structs, manual JSON serialization, or unstructured strings**:

1.  **Ad-hoc `AgentDescriptor` Struct**:
    *   *File*: `crates/op-agents/src/agent_catalog.rs:43-49`
    *   *Violation*: Expresses agent catalog contracts as ad-hoc Rust structs with generic string fields (`agent_type`, `name`, `description`, `operations`) instead of versioned Protobuf messages.
2.  **Ad-hoc `AgentSpec`, `AgentInstance` and `HealthCheck` Structs**:
    *   *File*: `crates/op-agents/src/agent_registry.rs:18-53, 66-77, 80-89`
    *   *Violation*: These critical orchestration structures are defined locally and serialized/deserialized dynamically via `simd-json`, skipping the formal schema definition process.
3.  **Ad-hoc D-Bus Task Payloads**:
    *   *File*: `crates/op-agents/src/agents/base.rs:12-32, 64-81`
    *   *Violation*: `AgentTask` and `TaskResult` are defined as local structs. They are serialized as raw JSON strings and sent across D-Bus. This makes schema evolution fragile and prone to decoding mismatches across versions.
4.  **Ad-hoc JSON Construction**:
    *   *File*: `crates/op-agents/src/agents/orchestration/memory.rs:236-258`
    *   *Violation*: The `serialize_memory_entries` function manually concatenates raw strings to build a JSON object. This bypasses structured schema contracts and lacks format validation.

## 6. Critical Security Vulnerabilities (Directly Exploitable)

### 6.1 CRITICAL: Systemic Path Traversal in Path Validation Bypass
*   **Citations**: 
    *   `crates/op-agents/src/agents/base.rs:279-301` (Broken `validate_path` implementation)
    *   `crates/op-agents/src/agents/content/docs_architect.rs:41-45` (Directly exploitable read)
*   **Vulnerability Mechanism**:
    The path validation logic used by traditional/legacy agents is implemented as follows:
    ```rust
    pub fn validate_path(path: &str, allowed_dirs: &[&str]) -> Result<String, String> {
        ...
        let is_allowed = allowed_dirs.iter().any(|dir| path.starts_with(dir));
        if !is_allowed { ... }
        Ok(path.to_string())
    }
    ```
    This function **fails to canonicalize the path** and does not search for directory traversal sequences (such as `..`) in `FORBIDDEN_CHARS`. 
    
    If the `allowed_dirs` list contains `/tmp`, an attacker can pass a path like `/tmp/../etc/passwd`. Because this string starts with `/tmp`, the validation passes. The uncanonicalized path is then passed directly to standard file operations:
    ```rust
    let validated_path = validation::validate_path(file, ALLOWED_DIRS)?;
    let content = std::fs::read_to_string(&validated_path)...
    ```
*   **Exploitation Scenario**: 
    An attacker sends a D-Bus method call or HTTP request targeting `DocsArchitectAgent` with `path` set to `/tmp/../etc/passwd` or `/home/user/../../../etc/shadow`. The agent will read and return the contents of any file on the host operating system that the running process has permission to access.
*   **Remediation**: Use `std::fs::canonicalize` on the path *before* performing prefix checks, or import the more robust validator from `crates/op-agents/src/security/validation.rs:90`, which explicitly rejects any path containing `..`.

### 6.2 CRITICAL: Sandbox Escape / Host Command Execution
*   **Citations**:
    *   `crates/op-agents/src/agents/language/python_pro.rs:33-51` (Direct `std::process::Command` execution)
    *   `crates/op-agents/src/agents/language/rust_pro.rs:35-51` (Direct host Cargo invocation)
    *   `crates/op-agents/src/agents/language/golang_pro.rs:31-48` (Direct host Go compiler invocation)
*   **Vulnerability Mechanism**:
    The crate defines a `SandboxExecutor` in `crates/op-agents/src/security/sandbox.rs` with robust configuration limits. However, **none of the compiled compiler/runtime agents use this sandbox**.
    
    Instead, they directly instantiate `std::process::Command` from the standard library:
    ```rust
    let mut cmd = Command::new("python3");
    ...
    let output = cmd.output().map_err(|e| format!("Failed to run python: {}", e))?;
    ```
    The commands run on the bare host system with the privileges of the parent D-Bus manager.
*   **Exploitation Scenario**:
    By invoking `python-pro` or `rust-pro` through D-Bus, an attacker can execute arbitrary code on the host operating system, entirely bypassing the sandbox restrictions defined in the `security/` module.
*   **Remediation**: Refactor the execution loop in all agents to route execution exclusively through `SandboxExecutor` rather than instantiating raw host `Command` processes.

### 6.3 CRITICAL: Key/Value JSON Injection in Memory Serialization
*   **Citation**: `crates/op-agents/src/agents/orchestration/memory.rs:247-251`
*   **Vulnerability Mechanism**:
    The `serialize_memory_entries` function manually constructs a JSON payload via raw string formatting:
    ```rust
    let entry_json = format!(
        "\"{}\":{{\"value\":\"{}\",\"memory_type\":\"{}\",\"tags\":[{}],\"created_at\":{},\"updated_at\":{},\"access_count\":{},\"last_accessed\":{}{}}}",
        key, entry.value, memory_type_str, tags_json, entry.created_at, entry.updated_at, 
        entry.access_count, entry.last_accessed, expires_json
    );
    ```
    No escaping is performed on `key` or `entry.value`.
*   **Exploitation Scenario**:
    If an attacker can store a memory key/value containing quotes and closing braces (e.g., `", "memory_type": "shared", "injected": "true"}`), they can inject arbitrary JSON keys, override other metadata attributes, or corrupt the entire database file upon serialization.
*   **Remediation**: Use `serde_json` or `simd-json` serialization builders to construct the JSON string safely.

## 7. Systemic Code Quality Findings

### 7.1 Thread-Blocking Race Condition in D-Bus Service Startup
*   **Citation**: `crates/op-agents/src/dbus_service.rs:291-292`
*   **Quality Issue**:
    ```rust
    // Wait for the service to be ready
    tokio::time::sleep(tokio::time::Duration::from_millis(100)).await;
    ```
    Relying on arbitrary sleeps to resolve initialization timing is an anti-pattern. Under high host system load, 100ms may be insufficient, causing downstream components to attempt connections before the D-Bus registry has completed registration.
*   **Remediation**: Await a notification or state event signaling that the D-Bus connection has successfully acquired the requested well-known name.

### 7.2 Unpadded Memory Safety Risk in Unsafe `simd_json` Deserialization
*   **Citation**: `crates/op-agents/src/dbus_service.rs:147`
*   **Quality Issue**:
    ```rust
    let task: AgentTask = unsafe { simd_json::from_str(&mut task_json_mut) }.map_err(...
    ```
    `simd_json::from_str` requires the input string to be mutable and padded with `simd_json::SIMDJSON_PADDING` bytes to prevent out-of-bounds reads during SIMD processing. Directly calling `unsafe { simd_json::from_str(&mut string) }` on an arbitrary `String` received over D-Bus without ensuring padding can cause undefined behavior or memory violations on specific architectures.
*   **Remediation**: Use safe parsing methods (`simd_json::from_slice` with a padded vector) or ensure padding constraints are strictly respected before invoking the unsafe parser.
