### Security & Quality Findings

#### [CRITICAL] Memory Safety & Out-of-Bounds Memory Read in Shared Memory Mmap
* **File Citation**: `crates/op-grpc-bridge/src/interceptor.rs:49-56`
* **Vulnerability Type**: Unvalidated Pointer Dereference / Denial of Service
* **Description**: The tonic gRPC interceptor attempts to perform a zero-copy direct read from the shared memory segment `/dev/shm/plugin_schema.dat`. It opens the file and immediately memory-maps it via `mmap2::MmapOptions::new().map(&file)`. However, the code performs absolutely no verification of the file's size before casting the raw pointer to `*const IdentitySled` and dereferencing its fields (`is_valid`, `hashed_footprint`). 
* **Exploitability**: If another process or an attacker truncates the `/dev/shm/plugin_schema.dat` file to 0 bytes, or to any size less than `std::mem::size_of::<IdentitySled>()` (minimum 73 bytes), the pointer dereference will access unmapped or out-of-bounds memory. This will cause an immediate Segmentation Fault, taking down the entire gRPC server gateway (Denial of Service). 
* **Data Race Hazard**: Furthermore, the pointer is accessed directly via raw pointer dereference `(*sled_ptr).is_valid` without volatile reads (`std::ptr::read_volatile`) or atomic synchronization, exposing the reader to data races under concurrent modifications by the writing process.
* **Remediation**: Check the file metadata length before calling `map()`. Ensure it is at least `std::mem::size_of::<IdentitySled>()`. Additionally, use volatile reads or structured synchronization primitives (e.g., `std::sync::atomic`) inside the sled layout to guarantee safe concurrent access.

#### [HIGH] Ad-Hoc Data Contracts and Stringified JSON Over D-Bus Bridge
* **File Citation**: `crates/op-grpc-bridge/src/grpc_server.rs:1039, 1083, 1118, 1150, 1198, 1229, 1308, 1426, 1451, 1515, 1564, 1608, 1699, 1715, 1763, 1839, 1888, 1974, 2038, 2091, 2131`
* **Vulnerability Type**: Violation of Schema-as-Code / Structural Typing Bypass
* **Description**: In multiple D-Bus boundary methods (e.g., `send_email`, `provision_user`, `admin_user_action`, etc.), the gRPC server serializes arguments into ad-hoc JSON strings using `simd_json::json!({ ... }).to_string()`, bypassing formal schemas and typed Protocol Buffers. It passes these raw strings over the local IPC channel to the D-Bus services. It then parses the stringified output using `serde_json::from_str(&result)`.
* **Exploitability**: This completely bypasses the Protocol Buffer compiler's safety guarantees and versioning controls. If the D-Bus backend introduces an unversioned contract change or updates a field type, the parser will fail at runtime, causing silent processing drops or unhandled deserialization panics.
* **Remediation**: Use the compiled Protobuf structures generated by `proto_gen.rs` or structured zvariant bindings to transmit typed parameters across IPC boundaries rather than serializing dynamic stringified JSON maps.

#### [HIGH] Unversioned C-Struct Mapping in Shared Memory Layout
* **File Citation**: `crates/op-grpc-bridge/src/interceptor.rs:16-27`
* **Vulnerability Type**: Memory Layout Fragility / ABI Drift
* **Description**: The `IdentitySled` is represented as an ad-hoc C-compatible struct (`#[repr(C)]`) mapped directly to raw bytes in `/dev/shm`. It does not use versioned serialization, schema negotiation, or magic byte headers.
* **Exploitability**: If the writer process (`op-identity`) is compiled with a slightly different toolchain version, different target options, or changes its internal field offsets without a synchronized update to `op-grpc-bridge`, the interceptor will read misaligned structure offsets. This results in memory layout corruption, leading to authentication bypasses (e.g. reading garbage bytes as `is_valid = true`) or undefined runtime behavior.
* **Remediation**: Refactor the shared-memory boundary to utilize a structured, versioned serialization format with deterministic offsets (such as FlatBuffers) or include a explicit schema version header check in the first 8 bytes of the shared-memory file.

#### [MEDIUM] Plaintext PII Leakage in Operational Logs
* **File Citation**: `crates/op-grpc-bridge/src/grpc_server.rs:1032, 1182, 1445, 1756, 1832, 1968, 2125`
* **Vulnerability Type**: Information Leakage / Privacy Compliance Violation
* **Description**: The gRPC server logs sensitive user PII in plaintext directly to standard output/system logs via `tracing::info!`.
  * `grpc_server.rs:1032`: Logs the sender (`from_email`), receiver (`to_email`), and plaintext `subject` line of all emails.
  * `grpc_server.rs:1832`: Logs plaintext user emails and administrative privileges when generating magic links.
  * `grpc_server.rs:1968`: Logs plaintext user emails during gRPC user registration.
* **Exploitability**: Operational logs are frequently forwarded to log aggregators, search indices (Elasticsearch/Splunk), and developer consoles. Plaintext storage of emails and email subjects violates privacy standards (GDPR/CCPA) and exposes users to target credential harvesting if logs are compromised.
* **Remediation**: Redact, mask, or hash user email addresses and subject lines (e.g., using Sha256 truncation) before passing them as fields to the logging macros.

#### [MEDIUM] Swallowed Errors on Critical Integration Failures
* **File Citation**: `crates/op-grpc-bridge/src/grpc_server.rs:1046, 1098, 1187, 1243, 1324, 1421, 1475, 1582, 1673, 1726, 1780, 1845, 1990, 2085, 2148`
* **Vulnerability Type**: Deficient Observability / Swallowed Errors
* **Description**: Multiple service boundaries swallow structural errors from the underlying D-Bus client inside `Err(_)` or `Err(_dbus_err)` arms without logging the root cause.
  * `grpc_server.rs:1046`: Swallows the D-Bus connection error if email sending fails, silently writing to a state store queue without diagnostic evidence.
  * `grpc_server.rs:1324`: Swallows network provisioning errors during `ensure_privacy_network` operations, failing silently from an observability perspective.
* **Exploitability**: System administrators and site reliability engineers will find it impossible to diagnose why integration backends are failing, as the bridge silently handles errors by caching "pending" actions in the local state store without alerting or logging the original D-Bus connectivity errors.
* **Remediation**: Replace ignored match bindings (e.g., `Err(_)`) with explicit error capture and log the root failure with `tracing::error!(%error, "...")` or `tracing::warn!`.

### Metrics Instrumentation Review

* **Prometheus Integration**: The `Cargo.toml` file includes the workspace dependency `prometheus = { workspace = true, features = ["process"] }`. However, there is no metrics compilation or direct instrumentation within the `op-grpc-bridge` codebase. 
* **State of Metrics**: No counters, histograms, or gauges are used to track request latencies, endpoint throughput, or D-Bus system bus error rates. 
* **Procedural Metrics**: The `RuntimeMirror` service (implemented in `grpc_server.rs:1022`) streams kernel-level memory metrics parsed manually from `/proc/meminfo` over gRPC to remote endpoints, but this does not represent internal application performance telemetry. Application-level gRPC middlewares should be introduced to collect standard RPC RED (Rate, Errors, Duration) metrics.
