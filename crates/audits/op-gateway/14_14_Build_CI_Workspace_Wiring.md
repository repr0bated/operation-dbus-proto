# SECURITY & CRYPTOGRAPHIC VULNERABILITIES

### 1. CRITICAL: Nonce Reuse across Restarts in Encrypted Key Storage
- **File & Line**: `crates/op-gateway/src/encrypted_storage.rs:324-329` (in `store_key`), and `crates/op-gateway/src/encrypted_storage.rs:260-264` / `295-299` (in `load_master_key` and `generate_master_key`)
- **Description**: The `EncryptedKeyStorage` uses ChaCha20-Poly1305 to encrypt stored keys. Nonces are generated using a simple counter starting from the state's `nonce_counter` field:
  ```rust
  let mut nonce = [0u8; 12];
  let nonce_counter = master_key.nonce_counter;
  nonce[4..12].copy_from_slice(&nonce_counter.to_le_bytes());
  master_key.nonce_counter += 1;
  ```
  However, `nonce_counter` is kept purely in-memory and is initialized to `0` whenever `load_master_key` or `generate_master_key` is called (which occurs on every startup/initialization of the storage manager).
- **Exploit Scenario**: If the gateway is restarted, the `nonce_counter` resets to `0`. If the application then stores any new keys, it will encrypt them using the exact same nonces (`0`, `1`, `2`, etc.) that were used prior to the restart under the exact same master key. A local attacker reading the encrypted files can perform standard ChaCha20 keystream reuse decryption attacks to recover WireGuard private keys and session keys.
- **Remediation**: Do not use a sequential counter that is reset on restart. Generate a cryptographically secure random 96-bit nonce using `SystemRandom` for every individual encryption operation.

### 2. CRITICAL: WireGuard Preshared Key (PSK) Derivation Bypass
- **File & Line**: `crates/op-gateway/src/wireguard_auth.rs:590-612` (in `derive_stable_psk`)
- **Description**: The WireGuard preshared key is derived using Argon2 with a static, hardcoded salt:
  ```rust
  let salt = b"WG-STABLE-PSK-2024";
  ```
  and an input vector comprised entirely of static, public, or easily observable data:
  ```rust
  let mut input = Vec::with_capacity(39);
  input.extend_from_slice(b"WG-PSK-");
  input.extend_from_slice(peer_key);
  ```
  The `peer_key` is the peer's public key, which is transmitted in plaintext over the wire and is public by definition.
- **Exploit Scenario**: Any network observer or local attacker can extract the client's public key from the network or service logs, execute the same public Argon2 derivation with the static salt `WG-STABLE-PSK-2024`, and calculate the exact "Preshared Key" for the connection. This completely defeats the security of the WireGuard PSK (which is meant to act as a symmetric secret for mutual authentication and post-quantum resistance).
- **Remediation**: Mix a high-entropy, server-side private master key (e.g. loaded from a secure file or physical token) into the KDF input so that third parties cannot derive the PSK.

### 3. CRITICAL: Predictable Session IDs and Session Hijacking
- **File & Line**: `crates/op-gateway/src/wireguard_auth.rs:395-401` (in `generate_session_id`) and `crates/op-gateway/src/wireguard_auth.rs:575-588` (in `generate_session_ids_batch`)
- **Description**: The session ID returned to clients is generated by hashing a string constructed solely from the peer's public key and the current Unix epoch time in seconds:
  ```rust
  let input = format!("WG-SESSION-{}-{}", peer_pubkey, Self::current_timestamp());
  ```
  This is then hashed using BLAKE2s.
- **Exploit Scenario**: Because the peer public key is public and the creation timestamp of a session can be easily approximated (or observed directly in server connection events), the search space for the timestamp is extremely small (a few thousand candidate seconds). An attacker can easily brute-force the BLAKE2s hash of candidate timestamps, compute the active session ID, and use it to call `validate_session` or bypass MCP gateway routing permissions.
- **Remediation**: Decouple the session ID entirely from public parameters or time. Generate the session ID as a high-entropy random value (e.g., 256 bits) generated directly from the cryptographically secure pseudo-random number generator (`SystemRandom`).

### 4. HIGH: Plaintext Storage of Encryption Master Key
- **File & Line**: `crates/op-gateway/src/encrypted_storage.rs:282-286` (in `generate_master_key`)
- **Description**: The master key used to protect all other encrypted keys is written directly to disk in plaintext:
  ```rust
  let mut key_data = Vec::with_capacity(64);
  key_data.extend_from_slice(&key);
  key_data.extend_from_slice(&salt);

  async_fs::write(path, &key_data).await?;
  ```
- **Exploit Scenario**: Although the file is created with `0600` permissions, any local attacker who can read filesystem backups, bypass DAC/MAC policies, or gain physical/cold-boot access can read `master.key` directly off the disk and instantly decrypt all WireGuard private keys and session keys.
- **Remediation**: Derivate the master key from a user-provided passphrase or secure hardware module on-the-fly rather than persisting the raw master key in plaintext on the filesystem.

### 5. HIGH: Silent Fallback to Unencrypted Key Storage
- **File & Line**: `crates/op-gateway/src/encrypted_storage.rs:144-152` (in `setup_native_btrfs_encryption`) and `crates/op-gateway/src/encrypted_storage.rs:219-223` (in `setup_luks_encryption`)
- **Description**: If the experimental Btrfs native encryption fails (which it will on standard kernels without experimental patches), the code silently falls back to unencrypted storage:
  ```rust
  if stderr.contains("encryption not supported") || stderr.contains("invalid option") {
      warn!("Native Btrfs encryption not supported, creating regular subvolume");
      self.create_regular_subvolume().await?;
  }
  ```
  Similarly, for LUKS, if the setup is triggered, it writes a warning and falls back to an unencrypted subvolume.
- **Exploit Scenario**: System administrators who deploy this gateway believing their critical security keys are encrypted at rest (as Btrfs native encryption or LUKS is enabled in the configuration) will have their keys stored entirely in plaintext because the system degrades silently without throwing an initialization error.
- **Remediation**: Fail loudly and refuse to initialize the storage manager if the requested encryption layer (Btrfs native or LUKS) cannot be established. Do not silently degrade to plaintext storage.

### 6. MEDIUM: Unsafe De-serialization in Database and File Deserializers
- **File & Line**: `crates/op-gateway/src/encrypted_storage.rs:388` (in `retrieve_key`), and `crates/op-gateway/src/wireguard_auth.rs:188` (in `load_wireguard_sessions`)
- **Description**: The code reads files from the filesystem and values from the SQLite database and deserializes them using unsafe `simd_json` blocks:
  ```rust
  let entry: EncryptedKeyEntry = unsafe { simd_json::from_str(&mut entry_str) }?;
  ```
- **Exploit Scenario**: If an attacker is able to modify key files on disk or corrupt columns in the SQLite database, passing unvalidated mutated strings to `unsafe { simd_json::from_str }` can lead to memory safety violations or undefined behavior (such as buffer over-reads).
- **Remediation**: Avoid `unsafe` parsing APIs. Use the safe, standard `simd_json::serde::from_slice` or validate inputs before deserialization.

### 7. MEDIUM: Command Execution via Insecure dd Invocation
- **File & Line**: `crates/op-gateway/src/encrypted_storage.rs:188-195` (in `setup_luks_encryption`)
- **Description**: The code executes an external shell command to create a container file:
  ```rust
  let output = Command::new("dd")
      .args([
          "if=/dev/zero",
          &format!("of={}", container_path.display()),
          "bs=1M",
          "count=100",
      ])
      ...
  ```
- **Exploit Scenario**: Relying on external binaries like `dd` is fragile and depends heavily on path resolution. While not directly injecting arguments here, the command can fail if the PATH environment is modified, leading to denial of service, or have unexpected interactions depending on the underlying OS implementation of `dd`.
- **Remediation**: Use native async Rust APIs to create and pad the file (e.g., `tokio::fs::File` with `set_len`).
