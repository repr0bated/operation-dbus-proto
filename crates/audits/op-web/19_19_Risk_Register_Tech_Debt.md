### Detailed Findings & Remediation

#### 1. IP Spoofing & Security Bypass via Untrusted Proxy Headers
* **Severity**: Critical (Directly exploitable)
* **File & Line**: `crates/op-web/src/middleware/security.rs:90`
* **Impact**: The `extract_ip` function parses `X-Forwarded-For` and `X-Real-IP` headers unconditionally from the incoming HTTP request. Because these headers are trusted without verifying whether the request was forwarded by a trusted reverse proxy (such as a local Nginx/Caddy server), an external attacker can append `X-Forwarded-For: 127.0.0.1` to their HTTP request. This forces the server to evaluate their `AccessZone` as `Localhost`, thereby bypassing all IP-based administrative restrictions.
* **Remediation**:
  Modify the `extract_ip` function to validate the peer address of the socket connection before reading proxy headers. If the peer address is not a trusted proxy, fallback to the socket IP:
  ```rust
  pub fn extract_ip(headers: &HeaderMap, addr: Option<&SocketAddr>) -> String {
      let peer_ip = addr.map(|a| a.ip());
      
      // Define trusted proxies (e.g., Localhost or specific internal subnets)
      let is_trusted_proxy = match peer_ip {
          Some(ip) => ip.is_loopback(),
          None => false,
      };

      if is_trusted_proxy {
          if let Some(forwarded) = headers.get("x-forwarded-for") {
              if let Ok(s) = forwarded.to_str() {
                  if let Some(client_ip) = s.split(',').next() {
                      return client_ip.trim().to_string();
                  }
              }
          }
      }

      addr.map(|a| a.ip().to_string()).unwrap_or_else(|| "0.0.0.0".to_string())
  }
  ```

#### 2. Complete Lack of Access Control Enforcement on Resolved AccessZone
* **Severity**: Critical (Directly exploitable)
* **File & Line**: `crates/op-web/src/routes/mod.rs:240` (and throughout handlers)
* **Impact**: The middleware `security::ip_security_middleware` successfully identifies the `AccessZone` and attaches it as a request extension. However, none of the administrative or tool endpoints (such as `POST /api/tool` or `POST /groups-admin/api/profiles/:name`) extract this extension to verify if the requester has the permissions required to run the operation. Because of this omission, any user—even those categorized as `Public`—can access administrative endpoints and invoke native shell/OVS/systemd tools.
* **Remediation**:
  Implement a guard middleware or extract the `AccessZone` extension in protected route handlers, returning `StatusCode::FORBIDDEN` if the zone is unauthorized:
  ```rust
  pub async fn enforce_admin_zone(
      Extension(zone): Extension<AccessZone>,
      request: Request,
      next: Next,
  ) -> Response {
      match zone {
          AccessZone::Localhost | AccessZone::TrustedMesh => next.run(request).await,
          _ => (StatusCode::FORBIDDEN, "Access Denied: Administrative privileges required").into_response(),
      }
  }
  ```

#### 3. Hardcoded Administrative Bypass API Keys (Backdoor)
* **Severity**: High
* **File & Line**: `crates/op-web/src/middleware/security.rs:13`
* **Impact**: The slice `BYPASS_API_KEYS` contains hardcoded API keys such as `"test-key-huggingface-2024"`. If an attacker discovers these keys (via source leak, reverse engineering, or public repositories), they can append them as `x-api-key` headers to instantly secure the highest level of administrative access (`AccessZone::TrustedMesh`), bypassing all system controls.
* **Remediation**:
  Remove all static, hardcoded credentials from the codebase. Retrieve authorized administrative tokens dynamically from an external vault, encrypted configuration, or environment variables at startup:
  ```rust
  lazy_static::lazy_static! {
      static ref BYPASS_API_KEYS: Vec<String> = {
          std::env::var("OP_ADMIN_BYPASS_KEYS")
              .unwrap_or_default()
              .split(',')
              .map(|s| s.trim().to_string())
              .filter(|s| !s.is_empty())
              .collect()
      };
  }
  ```

#### 4. Unencrypted Plaintext Storage of WireGuard Private Keys
* **Severity**: High
* **File & Line**: `crates/op-web/src/handlers/privacy.rs:135` and `crates/op-web/src/users.rs:32`
* **Impact**: During signup, the server generates a WireGuard keypair and stores the private key directly in the user database (`privacy-users.json`) via the `wg_private_key_encrypted` field. Despite the field name suggesting encryption, the raw, plaintext private key is written to disk. If the host filesystem or the `privacy-users.json` file is compromised, all user WireGuard private keys will be leaked in plaintext.
* **Remediation**:
  Encrypt the WireGuard private key using a secure symmetric encryption scheme (such as `aes-gcm` or `chacha20poly1305`) with a secret key derived from a secure master key stored outside the database.
  ```rust
  // Encrypt keypair.private_key before calling create_user
  let encrypted_private_key = encrypt_private_key(&keypair.private_key, &master_secret)?;
  ```

#### 5. Ad-Hoc JSON Contracts Violating Schema-As-Code Discipline
* **Severity**: High (Compliance / Quality)
* **File & Line**: `crates/op-web/src/mcp_compact.rs:24` (also `mcp.rs:40`)
* **Impact**: Data contracts for critical interfaces—including JSON-RPC payloads, system profiles, tool configurations, and OpenFlow states—are expressed as ad-hoc Rust structs or raw untyped JSON `Value` objects. This violates the repository's schema-as-code discipline, creating a high probability of structural drift, validation errors, and untracked API contract changes across system components.
* **Remediation**:
  Compile Protocol Buffer definitions (`.proto`) to specify versioned data contracts for all RPC messages, tool parameters, and Incus/OpenFlow configurations. Enforce strict JSON schema validation generated directly from these source-of-truth definitions during deserialization.

#### 6. Absence of OSCAL System Security Plan & Automated Control Audits
* **Severity**: High (Compliance Gap)
* **File & Line**: `crates/op-web/src/privacy_network.rs:65`
* **Impact**: Critical control-plane modifications—such as dynamically adding container interfaces, adding OpenFlow forwarding rules, and executing arbitrary system commands—are performed without machine-readable tracking, control validation, or policy constraints matching OSCAL criteria. This fails compliance requirements for continuous authorization and automated security posture management.
* **Remediation**:
  Export an OSCAL Component Definition containing metadata that maps active native-protocol controls (Netlink, OVSDB, D-Bus) to standard security frameworks (such as NIST SP 800-53). Emit structured compliance audit events matching these control IDs to `EventChain` when critical operations occur.

#### 7. Sensitive Magic Link Authentication Token Leakage to Console/Stdout
* **Severity**: Medium
* **File & Line**: `crates/op-web/src/email.rs:59`
* **Impact**: When the SMTP configuration is disabled or unconfigured, the application prints the generated magic link and raw token directly to stdout using `println!`. In production environments, standard output is frequently captured by centralized logging engines (e.g., Elasticsearch, AWS CloudWatch, journald). This exposes active credentials to unauthorized system observers.
* **Remediation**:
  Replace standard console output with a dedicated debug logger, and conditionally compile stdout fallbacks so that active credentials can never be printed in production mode:
  ```rust
  #[cfg(debug_assertions)]
  {
      println!("\n=== MAGIC LINK FOR TESTING ===");
      println!("Email: {}", to_email);
      println!("Link: {}", magic_url);
      println!("==============================\n");
  }
  #[cfg(not(debug_assertions))]
  {
      debug!("Generated magic link token for email target");
  }
  ```
