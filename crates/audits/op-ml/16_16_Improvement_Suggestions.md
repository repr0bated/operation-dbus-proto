2. Suggestion | Redesign model loading to occur during asynchronous startup instead of performing synchronous blocking operations during inference requests. | Rationale | The `ModelManager` currently uses a lazy on-demand initialization pattern. When a text needs to be embedded, if the model is not cached, it triggers `tokio::runtime::Handle::current().block_on` to run an asynchronous download from Hugging Face Hub, followed by loading the model into ONNX Runtime. Calling `block_on` from within an active Tokio runtime thread can lead to immediate runtime panics ("cannot start a runtime from within a runtime") or block worker threads for long periods while downloading large files (up to 420MB). Splitting this into an explicit async startup-phase initialization ensures the control plane is warm and fails fast if the network or disk is unavailable. | Example (crates/op-ml/src/model_manager.rs:188)

Suggestion | Adopt a strict, fallible builder pattern with validated types for execution settings instead of silent env-var parsing with fallbacks. | Rationale | `VectorizationConfig::from_env` parses execution providers and level parameters using custom strings and env vars, falling back silently to CPU execution or logging soft warnings when input is invalid. In production systems requiring deterministic compliance (e.g., FedRAMP physical isolation constraints), silently falling back from GPU acceleration (CUDA/TensorRT) to CPU can drastically drop throughput (from 19k/s to 2.8k/s) and mask underlying driver failures. The configuration parsing should return structured, strongly-typed errors to halt execution if requested hardware acceleration cannot be initialized. | Example (crates/op-ml/src/config.rs:199)
