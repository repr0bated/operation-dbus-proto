1. **Suggestion**: Unify D-Bus Interface Contracts via Versioned Schemas instead of Ad-hoc JSON Serialization | **Rationale**: The D-Bus interface currently serializes internal database/runtime states (`ServiceStatus`) into raw, unversioned JSON strings on the wire. This violates the schema-as-code discipline, bypassing Protobuf/OSCAL structural boundaries and risking silent parsing failures when clients and daemons undergo updates. The status contract should instead be explicitly defined in a Protobuf schema and exposed over D-Bus as a structured dictionary or GVariant. | **Example**: `crates/op-services/src/dbus/interface.rs:26`

2. **Suggestion**: Implement a Process Supervision/Monitoring Loop | **Rationale**: The `ProcessManager` spawns processes using `tokio::process::Command` but has no supervision routine to detect when a spawned child unexpectedly dies. This results in the internal state remaining `ManagerState::Running` while the actual process is dead (zombie state). A dedicated tokio supervision task or a signal-handling loop should actively manage and transition service status to `Failed` upon unexpected exit. | **Example**: `crates/op-services/src/manager/process.rs:13`

3. **Suggestion**: Use Zero-Copy Types (`Arc<str>` or `Bytes`) in `ServiceName` | **Rationale**: The codebase continuously clones `ServiceName` values and converts names back and forth between strings and `ServiceName` types. Transitioning `ServiceName` to internally wrap an `Arc<str>` or a zero-copy string representation would significantly reduce heap allocations and improve throughput under heavy management/event traffic. | **Example**: `crates/op-services/src/manager/service_manager.rs:205`

4. **Suggestion**: Migrate State Storage to Sled or CozoDB | **Rationale**: While SQLite via `sqlx` is serviceable, the workspace already references `cozo` with `storage-sled` features. A highly responsive system daemon benefits from a pure-Rust embedded store like `sled` or the relational model of `CozoDB`. This avoids the linking complexities of C-based SQLite dependencies and lowers query latency. | **Example**: `crates/op-services/src/store/mod.rs:9`

5. **Suggestion**: Enforce Structured Fields on Tracing Events | **Rationale**: Logging in `ServiceManager` uses unstructured messages, which are difficult to parse in log aggregators. Using tracing's structured fields (e.g., `tracing::info!(service = %name, pid = ?pid, "Started service")`) allows immediate, high-performance structured indexing of system changes. | **Example**: `crates/op-services/src/manager/service_manager.rs:56`

6. **Suggestion**: Apply the Typestate Pattern to Service State Transitions | **Rationale**: Currently, states are updated by manually matching enum options or passing parameters blindly. Defining the lifecycle of a service (e.g., `Service<Stopped>`, `Service<Starting>`, `Service<Running>`) as distinct Rust types prevents invalid transitions (like stopping a stopped service or setting a PID on a stopped service) at compile time. | **Example**: `crates/op-services/src/manager/service_manager.rs:205`

7. **Suggestion**: Implement Database-level Schema Enforcement for Definitions | **Rationale**: Service definitions are saved directly as raw stringified JSON payloads inside a TEXT column. Since there is no database-level schema validation, any schema drift or database corruption could prevent parsing of definition blobs during service startup. Database-level structured fields or JSON schema checks should enforce integrity constraints. | **Example**: `crates/op-services/src/store/mod.rs:24`

8. **Suggestion**: Introduce Batch Fetching APIs for Status Listing | **Rationale**: Currently, listing services or fetching status involves individually looking up each service, which can be inefficient on systems with dozens of active services. Providing unified bulk state-fetching minimizes thread contention and lock-acquisition overhead across both the database and the manager memory space. | **Example**: `crates/op-services/src/grpc/server.rs:222`
