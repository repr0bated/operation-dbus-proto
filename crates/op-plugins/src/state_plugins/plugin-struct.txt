● Yes — multi-collection retrieval is a first-class design feature, not a
  workaround.

  How it works

  Two ways to target multiple collections:
  1. Pass a collections: ["a","b",...] array in the tool args (the singular
  collection forces one; plural fans out).
  2. Pass nothing — and it uses per-mode defaults. For code_search/code_context
  (Search/Completion modes) the default is the whole
  DEFAULT_VOYAGE4_LITE_COLLECTIONS set — all 6 language collections fused
  automatically (rag_pipeline.rs:830). Overridable via env:
  COGNITIVE_MCP_SEARCH_COLLECTIONS, COGNITIVE_MCP_COMPLETION_COLLECTIONS,
  COGNITIVE_MCP_RAG_COLLECTIONS.

  Fusion mechanics (query_fused_collections, rag_pipeline.rs:501): embed the
  query once → search every collection with that one vector → merge → sort by
  score → dedupe by file → truncate to limit. Per-collection failures are
  non-fatal (logged and skipped), so one missing collection won't break the
  query.

  The one hard rule (and why it drives the rust-crate model choice)

  Because the query is embedded once with a single model and that vector is
  reused against every collection, fusion is only meaningful across collections 
  built with the same model. The code already enforces this by separating:
  - DEFAULT_VOYAGE4_LITE_COLLECTIONS → the fused set (6 collections, all
  voyage-4-lite)
  - DEFAULT_RUST_SOLO_COLLECTION = rust_lang_rust_lsp_voyage_code_3 →

  in a separate retrieval profile unless both indexing and querying use
