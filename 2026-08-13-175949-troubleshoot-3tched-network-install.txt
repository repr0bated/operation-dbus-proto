  A. The eth0 cutover never ran

  /etc/runit/sv/ovsbr0-eth0 is a symlink to ovsbr0-eth0.retired-20260806T012103Z
  (created Aug 9 17:56). The install's install -d / install -m followed it, so
  the new run and check landed in the retired dir — correct content, right
  effective place.

  But runsv started this service at 15:17 and the install wrote at 15:21, and
  step 4 only does sv start, which is a no-op on an already-running service. pid
  2783 is still executing the pre-15:21 run script:

  pid 2783 cwd  → /etc/runit/sv/ovsbr0-eth0.retired-20260806T012103Z
  pstree 2783   → sv check incus-ct-netmaker

  That old script waits on incus-ct-netmaker, whose check greps for
  NetMaker,RUNNING. NetMaker is STOPPED, so it blocks forever (676s and
  counting). ovsbr0-eth0-up was never reached.

  Result:

  ovs-vsctl show   → ovsbr0 ports: grpc0, svc0, pub0, ovsbr0 — no eth0
  pub0             → state DOWN, mac 2a:12:bd:cc:dd:08 (eth0 is
  36:f1:18:56:c4:6a), no address
  default route    → via 188.68.56.1 dev eth0   (should be dev pub0)

  sv status shows it green because runsv sees a live pid. The check script would
  catch it, but nothing consults the check after the start loop gives up.

  B. Every zcall step silently no-op'd

  zcall defaults to the session bus at /run/opdbus/session-bus.sock. That socket
  is served by a plain dbus-daemon (pid 2629) carrying only desktop names — no
  org.opdbus.* on it at all. The only opdbus name anywhere on this host is
  org.opdbus.v1.plugins.openflow on the system bus, claimed by op-of-controller.
  The parent tree org.opdbus.v1.plugins is claimed by nobody, on either bus —
  the only binary that requests it is op-xray-daemon
  (crates/op-xray-daemon/src/main.rs:118), which isn't running as a host
  service; xray-router runs upstream Xray inside the container instead.

  So zcall list returns rc=1 on both buses, wait-op-plugins exits "plugin tree
  not ready", and all of these failed into || warn: attach-controller-safe,
  ensure_fallback_normal, set_fail_mode, get-datapath-health, list_bridges,
  list_ports, and the container add_device calls.

  This is disguised because zcall methods openflow still works — it reads the
  sealed blob catalog (67 blobs in /dev/shm/opdbus/plugin-blobs), not the bus.
  The tree looks half-alive.

  C. The flow table has neither cookie class

  ovs-vsctl get bridge ovsbr0 controller   → []
  dump-flows ovsbr0 → cookie=0x0, priority=0 actions=NORMAL     ← the only entry

  op-of-controller is healthy — it logged "Loaded 4 static flow(s)" at 15:17:49
  and is listening on 10.200.0.1:6653 — but OVS never dials it (attach failed in
  B), so it never pushes them. The single flow present is OVS's own standalone
  default, not the FALLBACK cookie 0x…01 and not MANAGED 0x…02. The header's
  claim that the cookied fallback is what keeps the datapath forwarding isn't
  true right now.

  Script defects behind this

  1. sv start where sv restart is needed. Freshly installed run/check never take
  effect on a host where the service is already up. Only op-of-controller gets
  a restart, and that's the one service that was already fine.
  2. install follows the retired-dir symlink instead of resolving or refusing
  it. The Aug 6 retirement of ovsbr0-eth0 was never finished — the compat
  symlink is still the live path.
  3. Everything plugin-mediated is || warn. The script exits 0 having attached
  no controller, installed no flows, and performed no cutover. The one fatal
  guard (0-flow JSON) covers the thing that was already correct.
  4. Preflight checks command -v zcall but never that zcall can reach the tree.
  A single wait-op-plugins 5 in preflight would have caught B before anything
  was written.
  5. The sv check gate warns and continues after 60s — ovsbr0-eth0 was already
  hung at that point and the script proceeded to the OpenFlow section anyway.
  6. Header says containers have "no NICs, no incus proxy devices, anywhere" —
  that's actually accurate right now (all 8 checked, disk devices only), so
  --strip-legacy-devices is currently a no-op. But 4 of 8 are STOPPED (NetMaker,
  assistant, cozo, qdrant) and the convergence loop doesn't account for that.
  7. Minor: -h runs sed -n '2,50p' but the usage block is at lines 53-65, so
  --help cuts off before the options.

  Order to fix

  B blocks C, and A is independent. Suggested sequence: get a process publishing
  org.opdbus.v1.plugins on the session bus (or decide the tree lives on the
  system bus and fix zcall's default), then restart ovsbr0-eth0 so it runs the
  current script — that one moves the public address and default route onto
  pub0, so it should be done from console, not over SSH.

  Want me to patch the script (restart semantics, symlink resolution, fatal
  preflight on the plugin tree), or first chase why nothing owns
  org.opdbus.v1.plugins?

  The second one is the substantive error: 0x51820 is the mark WireGuard puts on
  its own encrypted packets to keep them on pub0. It's deliberately not the
  mark that selects the tunnel — the conf comments even warn "must NOT equal the
  application exit mark, or underlay loops into itself". So what's sealed today
  is the one value that must never be used for steering.

  For seal to actually drive routing, WgcfConfig needs to become a list — per
  tunnel: name, config_path, underlay fwmark, exit fwmark, table. Then

  from SHM, and anything opening a socket reads its exit mark from there rather
  than a hardcoded constant.
